# Spring Security 6 & JWT: Complete Execution Flow

## 1. System Setup & Configuration

**Sample Application Endpoints**

  

- `POST /api/auth/login` → Public
    
      
    
- `GET /api/orders` → Authenticated (`ROLE_USER`)
    
      
    
- `POST /api/orders` → Authenticated (`ROLE_USER`)
    
      
    

**Security Configuration**

  

Java

```
@Bean
public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
    http
        .csrf(csrf -> csrf.disable())
        .sessionManagement(session -> 
            session.sessionCreationPolicy(SessionCreationPolicy.STATELESS)
        )
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/api/auth/**").permitAll()
            .anyRequest().authenticated()
        )
        .addFilterBefore(
            jwtAuthenticationFilter, 
            UsernamePasswordAuthenticationFilter.class
        );

    return http.build();
}
```

## Phase 1: The Login Flow (`POST /api/auth/login`)

```
Client ──► HTTP Request ──► Servlet Container ──► SecurityFilterChain ──► AuthController
```

### Step-by-Step Execution

1. **Client Sends Credentials:** `POST /api/auth/login` with `{"username": "vinay", "password": "password123"}`.
    
      
    
2. **JWT Filter Skipping:** `JwtAuthenticationFilter` inspects the request. Finding no `Authorization: Bearer` header, it calls `filterChain.doFilter()` to pass execution along. The security policy (`permitAll()`) allows the unauthenticated request through.
    
      
    
3. **Controller Handling:** `DispatcherServlet` routes the request to `AuthController.login()`.
    
      
    
4. **Unauthenticated Token Creation:** The application creates an unauthenticated `UsernamePasswordAuthenticationToken(username, password)`.
    
      
    
5. **Manager Delegation:** The controller calls `authenticationManager.authenticate(token)`. `ProviderManager` delegates to `DaoAuthenticationProvider`.
    
      
    
6. **User Lookup:** `DaoAuthenticationProvider` calls `userDetailsService.loadUserByUsername("vinay")`, querying `UserRepository` -> Database.
    
      
    
7. **`UserDetails` Mapping:** The database returns the user record, mapped to a `UserDetails` instance:
    
      
    - **Username:** `vinay`
        
          
        
    - **Password Hash:** `$2a$10$...`
        
          
        
    - **Authorities:** `[ROLE_USER]`
        
          
        
    - **Enabled:** `true`
        
          
        
8. **Password Verification:** `DaoAuthenticationProvider` passes the raw password and hash to `passwordEncoder.matches("password123", storedHash)`:
    
      
    - **`true`** → Authentication succeeds.
        
          
        
    - **`false`** → Throws `BadCredentialsException` (401 response).
        
          
        
9. **Authenticated Object Created:** `AuthenticationManager` returns a fully authenticated `Authentication` token containing the `UserDetails` principal and granted authorities.
    
      
    
10. **JWT Generation & Delivery:** `jwtService.generateToken(authentication)` mints a signed JWT containing claims (`sub`, `roles`, `iat`, `exp`). The controller returns the token to the client.
    
      
    

## Phase 2: Protected Request Flow (`GET /api/orders`)

```
Client (Bearer JWT) ──► JWT Filter ──► Validate ──► SecurityContext ──► Authorization ──► Controller
```

### Step-by-Step Execution

1. **Header Parsing:** `GET /api/orders` arrives with `Authorization: Bearer <JWT>`. `JwtAuthenticationFilter` extracts the token string.
    
      
    
2. **Cryptographic Validation:** The filter validates signature, expiration (`exp`), issuer, and audience.
    
      
    - _If invalid/expired:_ Throws `ExpiredJwtException` or `JwtException` → 401 Unauthorized.
        
          
        
3. **Extract Identity:** Extracts claims (`sub` = `vinay`, `roles` = `["USER"]`).
    
      
    - **Option A (Stateless):** Build `Authentication` directly from JWT claims.
        
          
        
    - **Option B (Database Check):** Re-load user via `UserDetailsService` to verify account lock status or updated permissions.
        
          
        
4. **Context Injection:** Creates an authenticated `UsernamePasswordAuthenticationToken` (with `credentials = null`) and injects it into the framework:
    
      
    
    Java
    
    ```
    SecurityContextHolder.getContext().setAuthentication(authentication);
    ```
    
5. **FilterChain Continuation:** Calls `filterChain.doFilter(request, response)`.
    
      
    
6. **Authorization Check:** `AuthorizationFilter` checks rule `.anyRequest().authenticated()` against `SecurityContextHolder`. Access is granted.
    
      
    
7. **Controller Execution:** Request reaches `OrderController`. Logged-in user details are retrieved directly via `@AuthenticationPrincipal` or `SecurityContextHolder`.

## Key Interview Distinctions & Edge Cases

|**Scenario**|**Behavior**|**HTTP Status**|
|---|---|---|
|**Missing/Expired JWT**|Filter validation fails or missing context on protected route|**`401 Unauthorized`**|
|**Valid JWT, Insufficient Role**|User is `ROLE_USER`, route requires `ROLE_ADMIN`|**`403 Forbidden`**|
|**Does JWT "authenticate" the user?**|**No.** JWT is a signed token. Spring Security _validates_ it and constructs an `Authentication` object inside `SecurityContext` to achieve authentication.|—|

## Production Pitfalls Checklist

- **Forgetting `SecurityContextHolder`:** Simply validating a JWT does nothing unless you place the resulting `Authentication` object inside `SecurityContextHolder`.
    
      
    
- **Exposing Secrets in Claims:** JWT payloads are Base64URL-encoded (unencrypted). Never store passwords, PINs, or sensitive metadata in claims.
    
      
    
- **Filter Placement:** Always attach custom JWT filters relative to standard filters using `.addFilterBefore(jwtFilter, UsernamePasswordAuthenticationFilter.class)`.
    
      
    
- **Manual Authorization in Controllers:** Avoid writing `if (!user.hasRole())` checks manually inside controllers. Rely on `SecurityFilterChain` rules or `@PreAuthorize` annotations.
    
      
    

## FAQ Quick-Reference

- **Where is the JWT generated?** Inside the custom AuthService/Controller _after_ `AuthenticationManager` verifies credentials.
    
      
    
- **Does the JWT filter handle `/login`?** No. `/login` is a public controller endpoint that uses `AuthenticationManager`. The JWT filter skips `/login` and processes subsequent requests.
    
      
    
- **Why store `Authentication` in `SecurityContext`?** It makes user identity and granted authorities available to downstream Spring Security authorization filters and application components.
    
      
    

## 30-Second Interview Pitch

> "In a stateless JWT architecture using Spring Security 6, `/login` is a public endpoint. The controller receives credentials, wraps them in an unauthenticated `UsernamePasswordAuthenticationToken`, and passes it to `AuthenticationManager`. Upon successful validation via `UserDetailsService` and `PasswordEncoder`, we generate and return a signed JWT.
> 
>   
> 
> On subsequent API calls, the client passes the token in the `Authorization: Bearer` header. Our custom `OncePerRequestFilter` intercepts the request, validates the JWT, constructs an authenticated `Authentication` object, and registers it in the `SecurityContextHolder`. Spring Security's authorization filters then evaluate user authorities before dispatching the request to the controller."
