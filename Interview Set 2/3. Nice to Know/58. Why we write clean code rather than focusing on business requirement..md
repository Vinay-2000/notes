
Business requirements and delivery come first. Clean code is not something separate from delivering the requirement; it's about implementing the requirement in a way that's understandable and maintainable.

If I have a tight deadline, I won't over-engineer or spend unnecessary time making the code perfect. I'll implement the simplest solution that safely satisfies the requirement, while still maintaining basic standards like readability, proper naming, avoiding duplication where practical, and handling important error cases.

If there's a technical compromise because of the deadline, I'll make that trade-off explicit and create a follow-up task to address it rather than silently leaving technical debt.

### The key distinction

There are **three levels**:
```
Business requirement
        ↓
Must work correctly
        ↓
Clean + maintainable
        ↓
Beautiful / highly optimized / over-engineered
```

When the deadline is tight:
```
❌ Don't sacrifice correctness
❌ Don't introduce obvious bad code just to finish faster

✅ Avoid unnecessary abstraction
✅ Avoid premature optimization
✅ Keep code readable
✅ Deliver the required functionality
✅ Document/track technical debt
```

For example, suppose you need to build:

```
GET /users/{id}
```

You don't need to create:
```
UserServiceFactory
UserRepositoryFactory
UserResponseBuilder
UserStrategy
UserMapperFactory
```
just because "clean architecture" sounds good.

If a straightforward:
```
controller → service → repository
```


### If we have deadline to finish will you write pretty code.

I would write maintainable code, but I wouldn't optimize for pretty code at the expense of the deadline. My goal is the simplest correct solution. If the deadline forces a compromise, I'd make the technical debt visible and plan to address it later.
