Think of the JPA Entity Lifecycle like a **guest checking into a hotel**.

An entity object moves through **four main states** relative to the `EntityManager` (the hotel front desk) and the Database (the hotel rooms).

![[EntityLifecycle.png|627]]

## The 4 Entity States Explained

### 1. 🐣 Transient (New Object)

- **What it is:** You just instantiated a Java object using `new User()`.
    
- **Database Connection:** None. The database has no idea this object exists, and it has no primary key (`@Id`) assigned yet.
    
- **Analogy:** A walk-in guest waiting on the sidewalk outside the hotel.


```
User user = new User("Alice"); // TRANSIENT state
```

### 2. 🏠 Managed (Persistent)

- **What it is:** The entity is actively tracked by the `EntityManager` inside the **Persistence Context** (the 1st-level cache).
    
- **Magic Feature (Dirty Checking):** Any changes you make to this Java object fields will **automatically sync to the database** when the transaction commits — you don't even need to call `save()`!
    
- **Analogy:** The guest has checked in, received a room key, and is registered in the hotel system.


```
entityManager.persist(user); // Transitions to MANAGED
// OR
User user = entityManager.find(User.class, 1L); // Directly fetched as MANAGED

// Dirty checking in action:
user.setName("Alice Cooper"); 
// No repo.save() needed! JPA auto-detects the change and generates UPDATE on commit.
```

### 3. 🚪 Detached

- **What it is:** The entity exists in the database, but the `EntityManager` is no longer tracking it.
    
- **Why it happens:** The transaction ended, the session closed, or `entityManager.clear()` / `detach()` was explicitly called.
    
- **Analogy:** The guest has checked out. They still exist in the real world, but hotel room service won't update their room anymore.


```
entityManager.detach(user); // Transitions to DETACHED

user.setName("Alice Smith"); 
// Database will NOT be updated automatically anymore!

// To reconnect it back to Managed state:
User reattachedUser = entityManager.merge(user); // Back to MANAGED
```

### 4. 🗑️ Removed

- **What it is:** Scheduled for deletion. The entity is marked to be removed from the database when the transaction flushes.
    
- **Analogy:** Room reservation is canceled; housekeeping is on their way to clear the room.


```
entityManager.remove(user); // Transitions to REMOVED
// Fires 'DELETE FROM users WHERE id = ?' on transaction commit
```

## Summary Cheat Sheet

|**State**|**Tracked by EntityManager?**|**Has ID in Database?**|**Automatic DB Sync on Change?**|
|---|---|---|---|
|**Transient**|❌ No|❌ No|❌ No|
|**Managed**|✅ **Yes**|✅ Yes|✅ **Yes (Dirty Checking)**|
|**Detached**|❌ No|✅ Yes|❌ No|
|**Removed**|❌ No (Pending delete)|✅ Yes|❌ No (Will be deleted)|

## State Transition Methods at a Glance

- **`persist(entity)`** : `Transient` ➔ `Managed`
    
- **`find(Class, id)`** : Fetches directly into `Managed`
    
- **`detach(entity)`** or **`clear()`** : `Managed` ➔ `Detached`
    
- **`merge(entity)`** : `Detached` ➔ `Managed`
    
- **`remove(entity)`** : `Managed` ➔ `Removed`

> **Key Takeaway:** The magic of JPA (like auto-saving updates) **only works when an entity is in the Managed state**.

---
### Deep - merge
The biggest misconception about `entityManager.merge()` is that it converts your object into a managed object. **It doesn't!**

Instead, `merge()` **copies the state** of your unmanaged (detached or transient) object into a managed instance inside the Persistence Context and returns that **new managed instance**.

## What Happens Step-by-Step

When you call `User managedUser = entityManager.merge(detachedUser);`, JPA executes this algorithm:

1. **Checks the ID:** JPA looks at `detachedUser.getId()`.
    
2. **Finds or Fetches a Managed Instance:**
    
    - If an entity with that ID is **already in memory** (1st-level cache), JPA grabs it.
        
    - If it's **not in memory**, JPA fires a `SELECT` query to load it from the database into the Persistence Context.
        
    - If the ID is null or not found in the database, JPA creates a **brand new** managed instance (effectively acting like `persist()`).
        
3. **Copies Fields:** JPA copies all values from `detachedUser` onto the managed instance.
    
4. **Returns the Managed Instance:** It returns `managedUser`.
    
5. **Saves on Commit:** During dirty checking at transaction commit, JPA notices the changes on `managedUser` and issues an `UPDATE` statement.
    

## The Ultimate Trap: Original vs. Returned Object

This is where almost every JPA beginner gets burned:

Java

```
// 1. You pass a detached user with an updated name
detachedUser.setName("Updated Name");

// 2. You call merge
User returnedUser = entityManager.merge(detachedUser);

// 3. You change the ORIGINAL object again
detachedUser.setName("Another Change"); 
// ❌ WRONG! 'detachedUser' is STILL DETACHED! 
// This second change will NOT be saved to the database.

// 4. You change the RETURNED object
returnedUser.setName("This Will Save"); 
// ✅ CORRECT! 'returnedUser' is the MANAGED instance.
```

## `persist()` vs. `merge()` Summary

|**Feature**|**persist(entity)**|**merge(entity)**|
|---|---|---|
|**Intended Input State**|`Transient` (New, no ID)|`Detached` (Existing ID, unmanaged)|
|**Passes ID?**|Must **not** have an existing database ID|Usually has an existing ID|
|**DB Query Executed?**|Executes `INSERT` on commit|Executes `SELECT` (to load managed copy) then `UPDATE`|
|**Return Value**|`void` (Modifies original object in-place)|Returns **a new managed instance**|
|**Original Object State**|Becomes **Managed**|**Remains Detached**|

> **Rule of Thumb:** Always assign the result of `merge()` back to your variable:
> 
> `user = entityManager.merge(user);`
