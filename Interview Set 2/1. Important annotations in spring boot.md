@ - “Annotations in Java are metadata attached to classes, methods, or fields. They don’t execute any logic by themselves. Frameworks like Spring Boot read these annotations—usually via reflection or metadata scanning—and perform actions based on them. For example, when Spring sees `@Component`, it registers that class as a bean in the application context.”

### **@SpringBootApplication:** 
It is used to mark the main class of a Spring Boot application and serves as the entry point for running the application. And it combines three important annotations: @Configuration, @EnableAutoConfiguration, and @ComponentScan.
Use Cases:
1. Application Startup: Designate the main class of a Spring Boot application that will bootstrap the application context.
2. Configuration and Auto-Configuration: Enable automatic configuration and component scanning to simplify setup and reduce the need for explicit configuration.
3. Component Scanning: Automatically scan for and register components (beans) in the same package and its sub-packages.

```
Below is the source code for SpringBootApplication annotation:
@Target({ElementType.TYPE})
@Retention(RetentionPolicy.RUNTIME)
@Documented
@Inherited
@SpringBootConfiguration
@EnableAutoConfiguration
@ComponentScan(
    excludeFilters = {@Filter(
    type = FilterType.CUSTOM,
    classes = {TypeExcludeFilter.class}
), @Filter(
    type = FilterType.CUSTOM,
    classes = {AutoConfigurationExcludeFilter.class}
)}
)
public @interface SpringBootApplication
```

### **@Configuration:** 
This class contains bean definitions.

> @SpringBootConfiguration:
> is a specialized version of @Configuration used specifically in Spring Boot applications. It indicates that the class is a configuration class and inherits all the functionality of @Configuration, such as defining beans. Additionally, it helps Spring Boot identify the primary configuration class of the application.

### **@EnableAutoConfiguration:**
This enables Spring Boot’s auto-configuration mechanism, automatically configuring Spring beans based on what dependencies are present on the classpath. It is the feature that makes Spring Boot unique. It tells Spring Boot to automatically configure your application based on the dependencies in your classpath. 

```
@Import(AutoConfigurationImportSelector.class)  
public @interface EnableAutoConfiguration {  
}
```

> It uses `AutoConfigurationImportSelector` to load configuration classes from `META-INF` and applies them conditionally using annotations like `@ConditionalOnClass` and `@ConditionalOnMissingBean`. This reduces manual configuration and follows convention over configuration.

Spring Boot internally maintains a list of auto-configuration classes inside `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
During startup, `AutoConfigurationImportSelector` loads these classes and applies them conditionally based on classpath dependencies and existing beans.

| File                        | Purpose                                                    |
| --------------------------- | ---------------------------------------------------------- |
| `spring.factories`          | Older general Spring Boot extension registration mechanism |
| `AutoConfiguration.imports` | Modern Spring Boot auto-configuration registration         |
| `spring/aot.factories`      | Registers AOT/native-image related processors              |
`aot.factories` - Ahead Of Time processing
Normally Spring does lots of runtime work:
- reflection
- classpath scanning
- proxy generation
AOT tries to precompute this during build time.
This helps:
- faster startup
- lower memory
- native executable supports

### **@ComponentScan:**
This tells Spring to scan the package of the annotated class (and its sub-packages) for components like @Component, @Service, @Repository, and @Controller so that they can be registered as beans in the Spring context.
To scan other files under different hierarchy we can use
```
@ComponentScan(basePackages = {"com.app.service", "com.app.repo"})
```

We can exclude certain things from creating using below
```
@ComponentScan(
    basePackages = "com.example",
    excludeFilters = {
        @ComponentScan.Filter(
            type = FilterType.ASSIGNABLE_TYPE,
            classes = TestService.class
        )
    }
)
//ASSIGNABLE_TYPE - Exclude specific class.
//ANNOTATION - Exclude classes with certain annotation. like classes = Deprecated.class
//REGEX - Exclude by package/class pattern. pattern = "com.example.internal.*"
```

### **@Component:**  

> [!Generic stereotype annotation]
> A stereotype annotation is an annotation used to indicate the role of a class in the application architecture and to mark it as a Spring-managed component. @Component is called a generic stereotype annotation because it represents a general-purpose bean without implying any specific application layer or responsibility.
> All below are available in package - org.springframework.stereotype.*

It is a generic stereotype annotation used to mark a class as a Spring-managed bean. During component scanning, Spring detects classes annotated with @Component and registers them in the application context. It is typically used for classes that do not specifically belong to specialized stereotypes like @Service, @Repository, or @Controller.

### **@Service:**
It is a specialization of `@Component` used to mark classes that contain business logic or service-layer functionality. It is automatically detected during component scanning and registered as a Spring bean. 
Although it behaves the same as `@Component` technically, using `@Service` improves code readability and clearly indicates that the class belongs to the business layer. 
Its main value is:
- semantic clarity
- architecture separation
- AOP targeting conventions
Example -
```
@Before("@within(org.springframework.stereotype.Service)")  
public void log() {  
System.out.println("Service method called");  
}
```

### **@Repository:**  
It is another specialization of @Component. It is used specifically for classes that interact with the data access layer (e.g., database, file system).
You can use @Repository to indicate that a class provides mechanisms for CRUD (Create, Read, Update, Delete) operations and works with persistence mechanisms like databases. Spring also provides additional exception translation when you use @Repository, converting database-specific exceptions (e.g., SQL exceptions) into Spring's unified `DataAccessException` hierarchy. Spring uses `PersistenceExceptionTranslationPostProcessor` to do the translation.

### **@Controller:**  
It is a specialization of @Component that is used specifically for handling web requests in Spring MVC. Classes annotated with @Controller act as the presentation layer, typically handling incoming HTTP requests, processing them, and returning a response (often by rendering a view or returning data).
In backend controller, all the handler methods should return the logical **view** by returning String, view or `ModelAndView`.

> `ViewResolver` in Spring MVC is a component responsible for mapping logical view names returned by controllers to actual view resources like JSP or HTML files. It helps in separating business logic from the presentation layer by handling view resolution automatically. This makes the application more flexible and easier to maintain.
> It converts logical view names (e.g., "home") into actual view paths (e.g., /WEB-INF/views/`home.jsp`).

```
@Controller
public class HomeController {

@GetMapping("/home")
public String home() {
return "home";
	}
}
```

In Spring MVC with JSP, the controller fetches data and adds it to the `Model`. The returned String represents the view name, which is resolved to a JSP page. The JSP accesses model attributes using expression language like `${user.name}` and dynamically generates the final HTML response sent to the browser.
```
@Controller
public class UserController {

    @GetMapping("/profile")
    public String profile(Model model) { 

        User user = new User();
        user.setName("Vinay");
        user.setAge(25);

        model.addAttribute("user", user); //adds data into request scope/model

        return "profile";
    }
}
```

### **@RestController:**  
It is a Spring annotation that combines @Controller and @ResponseBody. It is used to create RESTful web services, where the methods in the controller return data directly as JSON or XML instead of a view.
### **@Controller  vs @RestController:**

|Aspect|`@Controller`|`@RestController`|
|---|---|---|
|Purpose|Used for traditional Spring MVC applications|Used for REST APIs / microservices|
|Main Usage|Returns views (JSP, Thymeleaf, Freemarker)|Returns data directly (JSON/XML/text)|
|Return Value Handling|Return value is treated as a **view name** by default|Return value is written directly to HTTP response body|
|Internal Composition|Normal stereotype annotation for MVC controllers|Combination of `@Controller` + `@ResponseBody`|
|Typical Flow|Request → Controller → ViewResolver → HTML View|Request → Controller → HttpMessageConverter → JSON/XML|
|View Resolution|Uses `ViewResolver` to resolve view names|No view resolution|
|Common Frontend Usage|Server-side rendered apps|React/Angular/mobile backend APIs|
|Response Format|HTML pages|JSON/XML/plain text|
|Default Behavior of `String` Return|Treated as logical view name|Treated as response body|
|JSON Conversion|Requires `@ResponseBody`|Automatic|
|Commonly Used With|JSP, Thymeleaf, MVC|REST APIs, SPA backends|
|Data Rendering|Server renders HTML|Client/frontend renders UI|

### **@Autowired:**  
It is a Spring annotation used for dependency injection. It allows Spring to automatically inject a required bean (dependency) into a class. The dependency can be injected at the field, constructor, or setter level.
However, constructor injection is preferred over field injection for several reasons, and if a class has only one constructor, Spring automatically injects the required dependencies without needing the @Autowired annotation. In that case, @Autowired is optional.
> Constructor injection is preferred because it makes dependencies explicit, supports immutability through final fields, improves unit testing, prevents partially initialized objects, and promotes cleaner architecture. It also helps detect circular dependencies early. For these reasons, constructor injection is considered the recommended dependency injection approach in modern Spring applications.
```
@Component
public class MyComponent {
    private final MyService myService;
    // Constructor injection: @Autowired is optional here
    public MyComponent(MyService myService) {
        this.myService = myService;
    }
```
Spring injects dependencies:
- by type first
- then by qualifier/name if multiple beans exist
- @Primary and @Qualifier("bean") can also be used incase of multiple beans
### **@Transactional:**  
It is a Spring Framework annotation used to manage transactions declaratively. When applied to a method or class, it ensures that the method runs within a transactional context. If the method completes successfully, the transaction is committed; if an exception occurs, the transaction is rolled back.
By default it rollbacks only for runtime exception and errors.
To rollback on checked exception we can use `@Transactional(rollbackFor = Exception.class)`
When placed on Class - all public methods are transactional by default.
Only works on public methods, not applied on private

It uses AOP proxy internally
Spring creates proxy around bean.
Proxy handles:
- begin transaction
- commit
- rollback

Self-invocation problem (COMMON INTERVIEW QUESTION)
This DOES NOT work properly:
```
public void outer() {    
	inner();
	}

@Transactional
public void inner() {}
```
Because:
- method call bypasses proxy
- transaction not applied

Propagation - How transactions interact with existing transactions
@Transactional(propagation = Propagation.xxx)

| Propagation Type     | Behavior                                                    |
| -------------------- | ----------------------------------------------------------- |
| `REQUIRED` (default) | Join existing transaction, else create new                  |
| `REQUIRES_NEW`       | Always create new transaction, suspend existing one         |
| `MANDATORY`          | Must run inside existing transaction                        |
| `SUPPORTS`           | Use existing transaction if present, else non-transactional |
| `NOT_SUPPORTED`      | Suspend existing transaction and run without transaction    |
| `NEVER`              | Must NOT run inside transaction                             |
| `NESTED`             | Create nested transaction/savepoint                         |

### Isolation - How concurrent transactions are isolated from each other
@Transactional(isolation = Isolation.xxx)

| Problem             | Think of it as                             |
| ------------------- | ------------------------------------------ |
| Dirty Read          | Reading unfinished work                    |
| Non-Repeatable Read | Same row changed mid-transaction           |
| Phantom Read        | New/deleted rows appearing mid-transaction |

| Isolation Level  | Dirty Read | Non-Repeatable Read | Phantom Read | What It Means                                                                                                  |
| ---------------- | ---------- | ------------------- | ------------ | -------------------------------------------------------------------------------------------------------------- |
| READ_UNCOMMITTED | ❌          | ❌                   | ❌            | Transactions can read even uncommitted changes made by other transactions                                      |
| READ_COMMITTED   | ✅          | ❌                   | ❌            | A transaction can only read data that has already been committed by other transactions                         |
| REPEATABLE_READ  | ✅          | ✅                   | ❌            | Once a transaction reads a row, repeated reads of the same row return the same data throughout the transaction |
| SERIALIZABLE     | ✅          | ✅                   | ✅            | Transactions execute as if they are running one after another sequentially                                     |
Default for most DBs like Oracle and PostgreSQL is READ_COMMITTED

### **@RequestMapping:**
@RequestMapping is key to routing client requests to the right controller method, whether it's for fetching data (GET), submitting data (POST), updating data (PUT), or deleting resources (DELETE).
It is a Spring annotation used to define URL patterns for controller methods. It helps route incoming HTTP requests to the appropriate methods in a Spring MVC controller. This annotation supports multiple HTTP methods like GET, POST, PUT, DELETE, etc., making it versatile for handling different types of requests.
It can be used at class level and method level - when used at class level it Defines common base path.
Instead of @RequestMapping(method = RequestMethod.GET) we can also use
@GetMapping  
@PostMapping  
@PutMapping  
@DeleteMapping  
@PatchMapping

> Content negotiation is the mechanism by which Spring determines the response format to return to the client based on request metadata such as the `Accept` header. Spring MVC uses `HttpMessageConverters` to automatically serialize response objects into formats like JSON or XML depending on client preference and available converters.
```
@GetMapping("/users/{id}")
public User getUser(@PathVariable Long id)

@RequestMapping(
    path = "/users",
    method = RequestMethod.GET,
    produces = "application/json" //Restrict supported response type.Now endpoint only returns JSON.
    consumes = "application/json" //Controls request body type accepted.Request body must be JSON.
)
```


### **@Profile:**
@Profile is a Spring annotation used to indicate that a bean or configuration should only be activated in specific environments or profiles. It allows for environment-specific configurations and bean definitions, making it easier to manage different settings for various environments (e.g., development, testing, production).  
Use Cases:
1. Environment-Specific Beans: Define beans that should only be available in certain environments, such as loading different data sources or services based on the active profile.
2. Conditional Configuration: Configure beans or settings conditionally based on the active profile, helping to separate development, test, and production configurations.
```
@Configuration
public class AppConfig {

    @Bean
    @Profile("dev")
    public MyService devService() {
        return new DevService(); // Bean for the development profile
    }

    @Bean
    @Profile("prod")
    public MyService prodService() {
        return new ProdService(); // Bean for the production profile
    }
}

// application.properties
spring.profiles.active=dev
```


### **@Bean:**
It is a Spring annotation used to explicitly define and register a bean in the Spring application context. It is typically used inside a `@Configuration` class, where the annotated method acts as a factory method and the returned object is managed by Spring as a bean.
It is commonly used for configuring third-party classes, external library objects, or complex bean initialization logic where source code cannot be modified.
By default, beans created using `@Bean` are singleton scoped, and Spring manages their full lifecycle including dependency injection, initialization, and destruction.
Normally, Spring uses: method name as bean name but we can give our own @Bean("paymentService") now we can use this with @Qualifier
> Inside `@Configuration` classes, Spring enhances the class using CGLIB proxies to ensure singleton behavior even when `@Bean` methods call each other internally. Example:
```
@Bean
public A a() {   
 return new A(b());
 }
 @Bean
 public B b() {    
 return new B();
 }
```

Spring ensures:  
✅ same singleton `B` bean reused  
instead of creating new object manually each call.

Lite mode (`@Bean` without `@Configuration`)

| Feature                                   | `@Configuration` | Lite Mode |
| ----------------------------------------- | ---------------- | --------- |
| CGLIB proxy enhancement                   | ✅                | ❌         |
| Intercepts `@Bean` method calls           | ✅                | ❌         |
| Ensures singleton reuse in internal calls | ✅                | ❌         |
| `@Bean` registration works                | ✅                | ✅         |
| Recommended for configuration classes     | ✅                | ❌         |
