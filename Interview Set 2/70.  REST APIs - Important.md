
> [!REST]
> REST stands for Representational State Transfer and API stands for Application Program Interface.
> It is a software architectural style that defines the set of rules to be used for creating web services. Web services that follow the REST architectural style are known as RESTful web services. 
> It allows requesting systems to access and manipulate web resources by using a uniform and predefined set of rules. Interaction in REST-based systems happens through the Internet's Hypertext Transfer Protocol (HTTP).


**REST API** must adhere to ==**six core architectural constraints**== to be considered truly RESTful. These principles, originally defined by Roy Fielding, decouple the client and server to maximize **scalability, simplicity, and modifiability** across the web.

There are six architectural constraints that makes any web service are listed below:
- Uniform Interface
- Stateless
- Cacheable
- Client-Server
- Layered System
- Code on Demand

### 1. Client-Server Architecture

The client (user interface) and the server (data storage and processing) must operate completely independently. The UI never needs to know how underlying data storage works, allowing both parts to evolve separately without tight coupling. This separation improves portability across multiple frontend platforms (such as web and mobile) while simplifying server scalability.

### 2. Statelessness

Every interaction between the client and the server must be entirely self-contained. The server does not store any context or session state about the client between requests. Consequently, every individual API request must include all necessary authentication credentials and parameters needed to process it. This ensures that any server replica can fulfill any request, significantly improving system reliability and scalability.

### 3. Cacheability

To optimize network performance, responses from the server must explicitly declare whether they can be cached by the client or intermediate proxies. When configured properly with HTTP caching headers, clients can reuse cached data for subsequent identical requests instead of querying the backend again. This leverages existing web caching infrastructure (browsers, CDNs, and proxy servers) to reduce server load and decrease latency.

```
Cache-Control: max-age=3600 //In headers
```

### 4. Uniform Interface

This is the central pillar that distinguishes a REST API from other API architectural styles. It mandates a standardized way for clients to interact with the server, regardless of application type, based on four core principles:

- **Resource Identification:** Abstract entities are uniquely identified using Uniform Resource Identifiers (URIs).
    
- **Manipulation through Representations:** Holding a representation of a resource (such as JSON data) gives the client enough context to modify or delete that resource on the server.
    
- **Self-Descriptive Messages:** Every request and response contains explicit metadata (such as HTTP verbs and content/media types) indicating how to process it.
    
- **HATEOAS (Hypermedia As The Engine Of Application State):** Server responses include dynamic hyperlinks guiding the client on what actions or related resources are available next.
    

### 5. Layered System

A client should not be able to tell whether it is connected directly to the primary server or to an intermediary. API infrastructure can incorporate multiple intermediate layers—such as load balancers, security gateways, reverse proxies, and Content Delivery Networks (CDNs)—without requiring changes to the client's code or workflow. This improves overall security, availability, and horizontal scaling.

### 6. Code on Demand _(Optional)_

This is the only optional constraint in REST. It permits servers to temporarily extend or customize client functionality by transferring executable code directly to the client. Examples include client-side scripts like JavaScript or compiled applets. While valid within the REST specification, this constraint is rarely implemented in modern production API designs.

---

HATEOAS (Hypermedia As The Engine Of Application State) means that a REST API should act like a website.

Spring Boot handles this by letting you wrap your data models inside an **`EntityModel`**, which automatically adds a `_links` object to your JSON output following the industry-standard **HAL (Hypermedia Application Language)** format.



Step 1: Add the Dependency

Add the Spring HATEOAS starter to your `pom.xml` (Maven) or `build.gradle`:

xml

```
<!-- Maven -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-hateoas</artifactId>
</dependency>
```

---


Step 2: Implement in the Controller

Instead of returning your raw `Order` entity directly, wrap it in an `EntityModel<Order>`.

Use Spring's **`WebMvcLinkBuilder`** to dynamically generate the URLs. This ensures that if your server host, port, or base paths change, the links will update automatically.


```
import static org.springframework.hateoas.server.mvc.WebMvcLinkBuilder.*;

import org.springframework.hateoas.EntityModel;
import org.springframework.hateoas.Link;
import org.springframework.web.bind.annotation.*;

@RestController
@RequestMapping("/orders")
public class OrderController {

    @GetMapping("/{id}")
    public EntityModel<Order> getOrderById(@PathVariable Long id) {
        // 1. Fetch your data from database (mocked here)
        Order order = new Order(id, "PENDING", 45.00);

        // 2. Build the link pointing to this specific method ("self" link)
        Link selfLink = linkTo(methodOn(OrderController.class).getOrderById(id)).withSelfRel();

        // 3. Create conditional business logic links
        EntityModel<Order> model = EntityModel.of(order, selfLink);

        if ("PENDING".equals(order.getStatus())) {
            // Add a link to pay for the order
            Link payLink = linkTo(methodOn(OrderController.class).payForOrder(id)).withRel("pay");
            // Add a link to cancel the order
            Link cancelLink = linkTo(methodOn(OrderController.class).cancelOrder(id)).withRel("cancel");
            
            model.add(payLink, cancelLink);
        }

        return model;
    }

    @PostMapping("/{id}/payments")
    public String payForOrder(@PathVariable Long id) {
        return "Order " + id + " paid successfully!";
    }

    @DeleteMapping("/{id}/cancel")
    public String cancelOrder(@PathVariable Long id) {
        return "Order " + id + " canceled!";
    }
}
```

Use code with caution.

---

Step 3: The JSON Output

When a client hits `GET /orders/9876`, Spring Boot will automatically format the output using standard HAL JSON formatting:

json

```
{
  "id": 9876,
  "status": "PENDING",
  "total": 45.0,
  "_links": {
    "self": {
      "href": "http://localhost:8080/orders/9876"
    },
    "pay": {
      "href": "http://localhost:8080/orders/9876/payments"
    },
    "cancel": {
      "href": "http://localhost:8080/orders/9876/cancel"
    }
  }
}
```

Use code with caution.

If you change the order status to `"SHIPPED"` in your database, the `if` block in your controller won't execute, and the `pay` and `cancel` links will completely disappear from the `_links` object automatically.
