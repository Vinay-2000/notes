# 1. What is Auto-Configuration?

Spring Boot **automatically configures your application based on the dependencies present in the classpath and your application configuration**.

For example, if you add:

```
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-jpa</artifactId>
</dependency>
```

Spring Boot can detect that JPA/Hibernate is available and automatically configure things such as:

- `DataSource`
- `EntityManagerFactory`
- Transaction infrastructure
- JPA repositories

You don't have to manually create all those beans.

---

# 2. The Important Idea: Conditional Configuration

Auto-configuration **doesn't blindly create everything**.

It uses conditions such as:

```
@ConditionalOnClass(...)
@ConditionalOnMissingBean(...)
@ConditionalOnProperty(...)
@ConditionalOnWebApplication
```

For example:

```
@Configuration
@ConditionalOnClass(DataSource.class)
@ConditionalOnMissingBean(DataSource.class)
public class DataSourceAutoConfiguration {

    @Bean
    public DataSource dataSource() {
        // ...
    }
}
```

Conceptually:

```
Is DataSource available?
        ↓
      YES
        ↓
Does user already have a DataSource?
        ↓
       NO
        ↓
Create/configure DataSource
```

This is why Spring Boot is often described as:

> **Convention over configuration.**

---

# 3. Where does Auto-Configuration get enabled?

The main entry point is:

```
@SpringBootApplication
public class Application {
}
```

`@SpringBootApplication` is actually a combination of three annotations:

```
@SpringBootConfiguration
@EnableAutoConfiguration
@ComponentScan
```

The important one here is:

```
@EnableAutoConfiguration
```

This tells Spring Boot:

> "Find the applicable auto-configuration classes and apply them."

---

# 4. What does `@EnableAutoConfiguration` do?

This is where things become interesting.

Spring Boot needs to know:

> **Which auto-configuration classes exist?**

Historically, Spring Boot used:

```
META-INF/spring.factories
```

Modern Spring Boot uses:

```
META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
```

This distinction is **very important in interviews**.

---

# 5. `META-INF` — What is it?

`META-INF` is a special directory inside a JAR.

For example:

```
spring-boot-autoconfigure-x.x.x.jar
│
├── META-INF/
│   ├── MANIFEST.MF
│   └── spring/
│       └── org.springframework.boot.autoconfigure.AutoConfiguration.imports
│
└── org/
    └── springframework/
        └── boot/
            └── autoconfigure/
                ├── jdbc/
                ├── web/
                ├── jpa/
                └── ...
```

Think of `META-INF` as containing **metadata/configuration about the JAR and frameworks using it**.

---

# 6. `AutoConfiguration.imports`

Modern Spring Boot uses:

```
META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
```

It contains the list of auto-configuration classes.

Conceptually:

```
org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration
org.springframework.boot.autoconfigure.orm.jpa.HibernateJpaAutoConfiguration
org.springframework.boot.autoconfigure.web.servlet.WebMvcAutoConfiguration
...
```

So Spring Boot can discover:

> "These are the auto-configuration classes available in the application."

---

# 7. Then Spring Boot evaluates conditions

Finding an auto-configuration class **doesn't mean it will necessarily be applied**.

Suppose:

```
@AutoConfiguration
@ConditionalOnClass(DataSource.class)
public class DataSourceAutoConfiguration {
}
```

Spring Boot checks:

```
AutoConfiguration.imports
        ↓
DataSourceAutoConfiguration
        ↓
Is DataSource on classpath?
        ↓
      YES
        ↓
Apply configuration
```

If the condition fails:

```
DataSource not available
        ↓
Condition fails
        ↓
Configuration skipped
```

---

# 8. Why does dependency matter?

Suppose you add:

```
spring-boot-starter-web
```

This brings Spring MVC-related dependencies onto the classpath.

Spring Boot sees those classes and says:

```
Spring MVC classes available?
        ↓
       YES
        ↓
Web MVC auto-configuration can apply
```

If you don't have the relevant dependencies, the corresponding auto-configuration generally won't activate.

This is called **classpath-based conditional configuration**.

---

# 9. What happens if I define the bean myself?

This is another major Spring Boot feature.

Suppose Boot wants to create:

```
DataSource
```

But you define:

```
@Bean
public DataSource dataSource() {
    return myDataSource();
}
```

Boot's auto-configuration may have:

```
@ConditionalOnMissingBean(DataSource.class)
```

So:

```
Boot checks:
"Does a DataSource already exist?"
        ↓
       YES
        ↓
Don't create the default one
```

This is why we say:

> **Auto-configuration is non-invasive.**

It provides defaults while allowing you to override them.

---

# 10. Auto-Configuration vs Component Scanning

This is a common interview trap.

### Component scanning

```
@Component
@Service
@Repository
@Controller
```

Spring finds **your application components** through component scanning.

### Auto-configuration

Spring Boot imports **predefined configuration classes provided by Boot/dependencies** based on conditions.

```
Component Scan
      ↓
Your application's beans

Auto-Configuration
      ↓
Framework/library configuration
```

They are different mechanisms.

---

# 11. `spring.factories` — What is it?

Older Spring Boot versions used:

```
META-INF/spring.factories
```

Example:

```
org.springframework.boot.autoconfigure.EnableAutoConfiguration=\
com.example.MyAutoConfiguration,\
com.example.OtherAutoConfiguration
```

Spring Boot would read this file to discover auto-configuration classes.

In **Spring Boot 3.x**, auto-configuration discovery uses:

```
META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
```

rather than the old `spring.factories` mechanism for auto-configuration imports.

However, `spring.factories` still exists for some other Spring Boot extension mechanisms, so don't say:

> "`spring.factories` is completely removed."

Better:

> "Spring Boot moved auto-configuration discovery from `spring.factories` to `AutoConfiguration.imports`."

# 12. How do we create our own Auto-Configuration?

This is a very useful advanced interview question.

Suppose you create a reusable library:

```
my-company-logging-starter
```

You could create:

```
@AutoConfiguration
@ConditionalOnClass(MyLogger.class)
public class MyLoggingAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean
    public MyLogger myLogger() {
        return new MyLogger();
    }
}
```

Then register it in:

```
META-INF/spring/
org.springframework.boot.autoconfigure.AutoConfiguration.imports
```

with:

```
com.mycompany.logging.MyLoggingAutoConfiguration
```

Now when another application adds your library:

```
Application
     ↓
adds your dependency
     ↓
Boot discovers AutoConfiguration
     ↓
checks conditions
     ↓
creates MyLogger
```

That's essentially how Spring Boot starters can provide automatic configuration.

---

# 13. Starter vs Auto-Configuration

Don't confuse these.

### Starter

A starter primarily gives you **dependencies**.

Example:

```
spring-boot-starter-data-jpa
```

It brings relevant dependencies such as Spring Data JPA, Hibernate, etc.

### Auto-Configuration

Provides the **configuration logic** that uses those dependencies.

Conceptually:

```
Starter
   ↓
Dependencies added
   ↓
Classes appear on classpath
   ↓
Auto-configuration detects them
   ↓
Conditions evaluated
   ↓
Beans configured
```

# 14. Full Flow — Remember This

This is probably the most useful diagram for your interview:

```
@SpringBootApplication
        │
        ↓
@EnableAutoConfiguration
        │
        ↓
Discover auto-configuration classes
        │
        ↓
META-INF/spring/
AutoConfiguration.imports
        │
        ↓
Candidate auto-configurations
        │
        ↓
Evaluate @Conditional*
        │
        ├── Condition fails → Skip
        │
        └── Condition passes
                    ↓
              Configuration applied
                    ↓
              Beans created
```

And dependencies influence the process:

```
Maven/Gradle dependency
        ↓
Classes available on classpath
        ↓
@ConditionalOnClass
        ↓
Auto-configuration activated
```

# 15. How to See What Auto-Configuration Happened?

Very useful for debugging/interviews.

Run your application with:

```
--debug
```

For example:

```
java -jar app.jar --debug
```

Spring Boot prints the **Condition Evaluation Report**.

It shows which auto-configurations:

- matched
- did not match
- and why

You can also enable relevant logging for deeper troubleshooting.

### Important example

If you put:
```
@Configuration
public class MyConfig {
    @Bean
    MyService myService() {
        return new MyService();
    }
}
```

inside your application's component-scan package → **bean gets created.**
But if this is inside a dependency JAR:

```
my-library.jar
└── com.example.MyConfig
```

and that package isn't component-scanned → **Spring won't magically find it.**
That's where `@AutoConfiguration` +:

```
META-INF/spring/
org.springframework.boot.autoconfigure.AutoConfiguration.imports
```

comes in.

So the mental model is:

> **`@Configuration` says "this is configuration."**  
> **`@AutoConfiguration` says "this is configuration that Spring Boot can automatically discover and conditionally apply."**
