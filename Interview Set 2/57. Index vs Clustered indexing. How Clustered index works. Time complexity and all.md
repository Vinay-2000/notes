
| Aspect                 | Clustered Index                                                                             | Non-Clustered Index                                                    |
| ---------------------- | ------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| **Storage**            | Determines how the table rows are physically/logically organized according to the index key | Separate structure from the table data, points to the actual table row |
| **Data location**      | Index structure contains/organizes the actual row data                                      | Index contains keys + pointers/locators to the actual rows             |
| **Number per table**   | Usually **one**                                                                             | Can have **multiple**                                                  |
| **Lookup**             | Can find the row directly through the clustered structure                                   | Finds the index entry first, then follows the pointer to the table row |
| **Range queries**      | Very efficient because rows are organized by the indexed key                                | Can also be efficient, but may require additional table lookups        |
| **Additional storage** | Generally doesn't require a separate copy of the row data                                   | Requires additional storage for the index                              |
| **Example**            | SQL Server clustered index                                                                  | SQL Server non-clustered index                                         |
| **Interview point**    | One table can have only one clustered ordering                                              | A table can have many non-clustered indexes                            |


### 1. What is a Clustered Index?

A clustered index determines the physical/logical ordering of the actual table data.
A **clustered index is an index where the leaf nodes contain the actual table rows**, and the rows are organized according to the index key.

Conceptually:

```
              B-Tree
             /      \
         [1,2,3]   [4,5,6]
            |          |
            ↓          ↓
       actual rows  actual rows
```

So the index and table data are effectively combined.

**Oracle note:** Oracle's normal tables do **not** work this way. The closest Oracle concept is an **Index-Organized Table (IOT)**.

### 2. Index vs Clustered Index

A normal/non-clustered index:

```
Index
  |
  | ID → ROWID
  ↓
Table
  |
  ↓
Actual row
```

The index is a **separate structure** from the table.

A clustered index:

```
Index
  |
  ↓
Actual table rows
```

The leaf level contains the actual data.

|                                     | Clustered         | Non-Clustered                           |
| ----------------------------------- | ----------------- | --------------------------------------- |
| What does leaf contain?             | Actual table data | Index key + row locator / included data |
| Determines table's ordering?        | Yes               | No                                      |
| Number per table                    | Usually one       | Can have many                           |
| Range queries                       | Very efficient    | Can be efficient                        |
| Extra lookup to row?                | Usually no        | Often yes                               |
| Index itself represents table data? | Yes               | No                                      |

### 3. How does a Clustered Index work?

Suppose the clustered key is `id`.

The B+Tree might look like:

```
                     [50]
                    /    \
              [20,30]    [70,90]
                /           \
               ↓             ↓
        actual rows       actual rows
```

The leaf level contains the actual rows:

```
[10, A, 50000]
[20, B, 60000]
[30, C, 70000]
...
[50, X, 80000]
...
```

For:

```
WHERE id = 70
```

the database:

```
Root
 ↓
Intermediate node
 ↓
Leaf containing 70
 ↓
Actual row
```

Search complexity:

```
O(log N)
```

For:

```
WHERE id BETWEEN 70 AND 100
```

it finds `70` and then scans the neighboring leaf entries/pages:

```
O(log N + K)
```

where `K` = number of matching rows.

**The key advantage:** because the actual rows are organized by the clustered key, nearby key values are physically/logically close, making range scans efficient.

For **Oracle specifically**, keep in mind: normal Oracle tables use separate B-tree indexes + `ROWID`; **IOTs** are the Oracle feature where the table data itself is stored in the primary-key B-tree.

#### What is ROWID in Oracle?

**ROWID is Oracle's physical address/locator of a row in a table.**
It tells Oracle **where the row is physically stored** so Oracle can locate it quickly.

Example:

```
SELECT id, ROWID
FROM index_test;
```

You saw something like:

```
ID    ROWID
1     AAAR2VAAYAAAAA+AAA
2     AAAR2VAAYAAAAA+AAB
3     AAAR2VAAYAAAAA+AAC
```

That `AAAR2VAAYAAAAA+AAA` is the row's **ROWID**.

### What does it represent?

Conceptually, a ROWID identifies:

```
Database
   ↓
Data Object
   ↓
Data Block
   ↓
Row within the block
```
