A **cyclic dependency** (or circular dependency) occurs when two or more components—such as classes, modules, packages, or Spring beans—depend on each other directly or indirectly, creating an unbreakable loop.

In a Spring Boot application, if **Bean A** needs **Bean B** to be created, but **Bean B** needs **Bean A** to be created, Spring gets stuck in an infinite loop during startup and throws a `BeanCurrentlyInCreationException`.

## 1. When Do We Get It?

Cyclic dependencies usually arise due to **poor architecture or tight coupling**. Common real-world scenarios include:

- **Direct Dependency Loop (A ↔ B):**
    
    - `UserService` needs `NotificationService` to send a welcome email.
        
    - `NotificationService` needs `UserService` to look up recipient user preferences.
        
- **Indirect Dependency Loop (A → B → C → A):**
    
    - `OrderService` depends on `PaymentService`.
        
    - `PaymentService` depends on `InventoryService`.
        
    - `InventoryService` depends back on `OrderService`.
        
- **Constructor Injection (Most Common Exception Trigger):**
    
    Since Spring Boot 2.6+, **circular references are disabled by default**. When using mandatory **Constructor Injection** (which is best practice), Spring cannot instantiate either bean because neither can be created first without the other already existing.
    

## 2. Example of a Cyclic Dependency

Java

```
@Service
public class UserService {
    private final NotificationService notificationService;

    // UserService needs NotificationService
    public UserService(NotificationService notificationService) {
        this.notificationService = notificationService;
    }
}

@Service
public class NotificationService {
    private final UserService userService;

    // NotificationService needs UserService -> BOOM! Circular Dependency
    public NotificationService(UserService userService) {
        this.userService = userService;
    }
}
```

When you run this application, Spring Boot fails at startup with:

> `Action: Rethink the design of your application or break the cycle by configuring one of the beans to be injected lazily.`

## 3. How to Resolve It

Resolving cyclic dependencies ranges from **architectural fixes** (best practices) to **quick-fix annotations** (workarounds).

### Strategy 1: Architectural Refactoring (Best Approach)

The primary cause of circular dependency is that a single service is doing too much or holding mixed responsibilities.

#### A. Extract the Shared Logic into a Third Service

Create a new service (e.g., `UserPreferenceService`) to hold the common functionality both services need, breaking the cycle into `A → C` and `B → C`.

```
Before:  [ UserService ] <---> [ NotificationService ]

After:   [ UserService ] ----> [ UserPreferenceService ]
                                        ^
         [ NotificationService ] -------|
```

#### B. Use Event-Driven Architecture (Application Events)

Instead of `UserService` directly invoking `NotificationService`, have `UserService` publish a domain event. `NotificationService` simply listens for that event.

Java

```
@Service
public class UserService {
    private final ApplicationEventPublisher eventPublisher;

    public UserService(ApplicationEventPublisher eventPublisher) {
        this.eventPublisher = eventPublisher;
    }

    public void registerUser(User user) {
        // Save user logic...
        eventPublisher.publishEvent(new UserRegisteredEvent(user));
    }
}

@Service
public class NotificationService {
    @EventListener
    public void handleUserRegistered(UserRegisteredEvent event) {
        // Send email logic without needing UserService injected
    }
}
```

### Strategy 2: Quick Framework Fixes (Workarounds)

If refactoring isn't immediately possible (e.g., legacy codebases), Spring provides tools to break initialization loops.

#### A. Use `@Lazy` Annotation

Adding `@Lazy` tells Spring to inject a **proxy** instead of a fully initialized bean instance at startup. The actual bean is initialized only when its methods are called for the first time.

Java

```
@Service
public class UserService {
    private final NotificationService notificationService;

    public UserService(@Lazy NotificationService notificationService) {
        this.notificationService = notificationService;
    }
}
```

#### B. Use Setter or Field Injection

Constructor injection requires dependencies at creation time. Setter injection allows Spring to construct both beans first via default constructors and inject the dependencies afterwards.

Java

```
@Service
public class UserService {
    @Autowired
    private NotificationService notificationService; // Setter/Field injection delays resolution
}
```

#### C. Enable Circular References globally in `application.properties`

_(Not recommended for long-term production code, but helpful as a temporary stopgap)_

Properties

```
spring.main.allow-circular-references=true
```

## Summary Comparison

| **Resolution Strategy**    | **Code Quality Impact** | **Ideal Use Case**                                       |
| -------------------------- | ----------------------- | -------------------------------------------------------- |
| **Extract Shared Service** | 🌟 Excellent            | Permanent fix; promotes clean separation of concerns.    |
| **Event-Driven Listener**  | 🌟 Excellent            | Decoupling domain actions (e.g., orders, notifications). |
| **`@Lazy` Annotation**     | ⚠️ Moderate             | Quick patch when refactoring is too costly right now.    |
| **Setter Injection**       | ⚠️ Moderate             | Legacy codebase refactoring.                             |
| **Global Property Flag**   | 🔴 Low                  | Quick testing or emergency fixes during migrations.      |
