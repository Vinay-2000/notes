**Transaction Isolation** defines how one transaction is isolated from other concurrent transactions and controls issues such as dirty reads, non-repeatable reads, and phantom reads. Spring supports four isolation levels: Read Uncommitted, Read Committed, Repeatable Read, and Serializable. 

**Transaction Propagation** defines how transactions behave when one transactional method calls another. The default propagation is `REQUIRED`, which joins an existing transaction or creates a new one if none exists. Other common propagation types include `REQUIRES_NEW`, which always starts a new transaction, and `SUPPORTS`, which joins an existing transaction if available. Isolation focuses on concurrency between transactions, while propagation focuses on transaction behavior across method calls.
## What is Isolation?

Isolation determines **how one transaction is affected by other concurrent transactions**.

Imagine two users accessing the same database row at the same time.
Isolation decides:
- Can Transaction B see uncommitted changes of Transaction A?
- Can the same query return different results?
- Can new rows suddenly appear?

Dirty read happens when reading uncommited data like if another transaction sets a value without commiting and a different one reads that value it will be a Dirty read since there is no surety that the other transaction will commit that value.

Non-repeatable read(Same row changes) when we do a select from table and it returns a value and later we do same select again and we get a different value because of any commits from other transactions will be called as Non-repeatable read. 

Phantom Read is when new (or deleted) rows appear/disappear on the following read.

| Non-Repeatable Read      | Phantom Read                           |
| ------------------------ | -------------------------------------- |
| Same row changes         | Result set changes                     |
| Caused by `UPDATE`       | Usually caused by `INSERT` or `DELETE` |
| Existing record modified | Rows appear/disappear                  |
### Four Isolation Levels
| Isolation Level      | Dirty Read  | Non-Repeatable Read | Phantom Read | How it works                                                                                                                                                                                                                                                                                                  |
| -------------------- | ----------- | ------------------- | ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Read Uncommitted** | ❌ Allowed   | ❌ Allowed           | ❌ Allowed    | No locking or waiting. Transactions can read even **uncommitted changes** made by other transactions. Fastest but least safe.                                                                                                                                                                                 |
| **Read Committed**   | ✅ Prevented | ❌ Allowed           | ❌ Allowed    | A transaction can only read **committed data**. If another transaction has modified a row but not committed, it must wait or read the last committed version. However, once that transaction commits, subsequent reads can see the new value.                                                                 |
| **Repeatable Read**  | ✅ Prevented | ✅ Prevented         | ❌ Allowed    | Once a transaction reads a row, that row cannot be modified by other committed transactions for the duration of the transaction (implementation varies by database). Reading the **same row** again always returns the same values. However, **new rows** matching the query can still appear (phantom rows). |
| **Serializable**     | ✅ Prevented | ✅ Prevented         | ✅ Prevented  | Transactions execute as if they were running **one after another** (or the database enforces an equivalent effect using locks or serialization techniques). Prevents updates and inserts/deletes that would affect another transaction's result set, making it the safest but slowest isolation level.        |

```
@Transactional(
    isolation = Isolation.READ_COMMITTED
)
```


| Propagation        | Meaning                                                  |
| ------------------ | -------------------------------------------------------- |
| REQUIRED (Default) | Join existing transaction or create one                  |
| REQUIRES_NEW       | Suspend (Pause) current transaction and create a new one |
| SUPPORTS           | Join if exists, otherwise execute without transaction    |
| NOT_SUPPORTED      | Suspend transaction and execute without one              |
| MANDATORY          | Must already have a transaction                          |
| NEVER              | Must not have a transaction                              |
| NESTED             | Nested transaction using savepoints                      |
### Q: Default Isolation?

Depends on the database.
Spring uses the database default.

Examples:
- Oracle → Read Committed
- PostgreSQL → Read Committed
- MySQL (InnoDB) → Repeatable Read
