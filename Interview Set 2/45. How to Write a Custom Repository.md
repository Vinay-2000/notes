When standard repository methods aren't enough—such as when you need complex dynamic queries via `EntityManager` or Criteria API—Spring Data JPA lets you create a **Custom Repository Fragment**.

Spring uses a strict naming convention: your implementation class must end with **`Impl`** (e.g., `UserRepositoryCustomImpl`) so Spring can wire it automatically.

**1.1. Create the Custom Interface:**
Define custom signatures.

Declare an interface containing only your complex/custom method signatures.


```
public interface UserRepositoryCustom {
    List findUsersWithComplexFilters(String emailDomain, Integer minAge);
}
```

**2.2. Implement using Impl suffix:**
Inject EntityManager.

Implement the interface. Name the class `UserRepositoryCustomImpl` and use `@PersistenceContext` to inject the low-level `EntityManager`.


```
import jakarta.persistence.EntityManager;
import jakarta.persistence.PersistenceContext;
import java.util.List;

@Repository
public class UserRepositoryCustomImpl implements UserRepositoryCustom {

    @PersistenceContext
    private EntityManager entityManager;

    @Override
    public List findUsersWithComplexFilters(String emailDomain, Integer minAge) {
        String jpql = "SELECT u FROM User u WHERE u.email LIKE :domain AND u.age >= :minAge";
        return entityManager.createQuery(jpql, User.class)
                .setParameter("domain", "%" + emailDomain)
                .setParameter("minAge", minAge)
                .getResultList();
    }
}
```

**3.3. Extend from Main Repository:**
Combine standard + custom.

Have your main `JpaRepository` extend both `JpaRepository` **and** your custom interface.


```
@Repository
public interface UserRepository extends JpaRepository, UserRepositoryCustom {
    // Keeps all default CRUD methods + custom method automatically!
}
```

# Deep
- Spring uses a strict naming convention: your implementation class must end with **`Impl`** - Why?

## Without any implementation

Suppose you have

```
public interface EmployeeRepository
        extends JpaRepository<Employee, Long> {
}
```

You never write

```
class EmployeeRepositoryImpl
```

Spring Data generates a proxy automatically at runtime.

---

## Now suppose you add a custom interface

```
public interface EmployeeRepositoryCustom {

    List<Employee> search(String name);
}
```

and extend it

```
public interface EmployeeRepository
        extends JpaRepository<Employee, Long>,
                EmployeeRepositoryCustom {
}
```

Now Spring knows:

> "EmployeeRepository has some methods I don't know how to implement."

It needs to find your implementation.

---

## How does it find it?

Spring Data looks for a class with the default postfix `Impl`.

```
EmployeeRepositoryCustom
        ↓
EmployeeRepositoryCustomImpl
```

or, depending on the setup, it may also associate the implementation with the repository fragment using the configured postfix.

If it finds

```
@Repository
public class EmployeeRepositoryCustomImpl
        implements EmployeeRepositoryCustom {
}
```

it combines:

```
Generated JpaRepository methods
            +
Your custom implementation
            =
Final EmployeeRepository bean
```

---

## Why use `Impl`?

Imagine there are 500 classes.

```
EmployeeService

EmployeeDAO

EmployeeManager

EmployeeSearch

EmployeeHelper

EmployeeSomethingElse
```

Spring needs a deterministic way to identify:

> "This class implements the custom repository fragment."

Instead of scanning every class and guessing, it follows a convention.

```
Interface
        ↓
EmployeeRepositoryCustom

Implementation
        ↓
EmployeeRepositoryCustomImpl
```

This makes startup simpler and avoids ambiguity.

---

## What happens internally?

Very roughly, Spring does something like this:

```
String implementationName =
    interfaceName + "Impl";
```

Then it checks:

```
Does EmployeeRepositoryCustomImpl exist?
```

If yes:

```
Instantiate it

↓

Inject EntityManager

↓

Merge it with JpaRepository proxy

↓

Return EmployeeRepository bean
```

---

## Can we change `Impl`?

Yes.

The postfix is configurable.

```
@EnableJpaRepositories(
    repositoryImplementationPostfix = "Custom"
)
```

Now Spring looks for

```
EmployeeRepositoryCustom
        ↓
EmployeeRepositoryCustomCustom
```

or whatever postfix you've configured.

So **`Impl` is just the default convention**, not a hard requirement.

---

## Is this a Spring Framework rule?

**No.**

This convention belongs to **Spring Data JPA (and Spring Data repositories)**.

For normal Spring beans, you can name implementation classes however you like:

```
@Service
public class EmployeeServiceV2
        implements EmployeeService {
}
```

or

```
@Component
public class MyAwesomeImplementation
        implements PaymentGateway {
}
```

Spring doesn't care about the class name because it discovers these beans through component scanning and dependency injection, not by a repository naming convention.

### Interview answer

> The `Impl` suffix isn't a general Spring rule. It's the default naming convention used by Spring Data repositories to locate custom repository implementations. When a repository extends a custom interface, Spring Data looks for an implementation with the configured postfix (default: `Impl`) and composes it with the generated `JpaRepository` proxy. The postfix is configurable using `@EnableJpaRepositories(repositoryImplementationPostfix = "...")`.
