**Difference between Error and Exception?**

> Errors represent serious JVM-level problems that applications typically cannot recover from. Exceptions represent application-level problems that can usually be handled.

# Checked Exceptions
Compiler forces you to handle them. We must either handle them using try catch or Declare in class signature with throws.
# Why Called Checked?
Because compiler checks them at compile time.
Before the code runs, compiler ensures:

> "Have you handled this exception?"

| Checked                  | Unchecked                       |
| ------------------------ | ------------------------------- |
| Compiler forces handling | Compiler doesn't force handling |
| Extends Exception        | Extends RuntimeException        |
| Compile-time check       | Runtime check                   |
| Ex: IOException          | Ex: NullPointerException        |
## throw
Used to actually create and throw an exception.
```

```
## throws
Used in method signature.
```

```

## Try-with-resources
> It automatically closes resources and avoids resource leaks. The resource must implement AutoCloseable.
```
public interface AutoCloseable {
    void close() throws Exception;
}
```
The important thing is that `close()` is called even if an exception occurs.
Since `Closeable` extends `AutoCloseable`, they can all be used in try-with-resources.

With try At least **one of `catch` or `finally` must be present**.

Can a `try` block exist **without catch and finally** if it's a **try-with-resources**?
✅ Yes.
```
try (FileReader reader = new FileReader("test.txt")) {    
// use reader
}
```
This is valid because Java automatically generates the resource cleanup logic behind the scenes.

### If there are multiple resources, in what order are they closed?

```
try (
Resource1 r1 = new Resource1(); 
Resource2 r2 = new Resource2()) {}
```
They are closed in **reverse order**:
```
r2.close()
r1.close()
```

## ResponseEntity

_ResponseEntity_ **represents the whole HTTP response: status code, headers, and body**. As a result, we can use it to fully configure the HTTP response.

Refer: https://www.baeldung.com/spring-response-entity
# Why Return ResponseEntity?
Because it lets us control:
```
return ResponseEntity        
			.status(404)       
			 .body(...);
```
- Status code
- Headers
- Response body
all in one place.
---
When an endpoint returns successfully, Spring provides an HTTP 200 (OK) response.

If we want to specify the **response status of a controller method**, we can mark that method with @ResponseStatus.
@ResponseStatus(HttpStatus.I_AM_A_TEAPOT)
@ResponseStatus(HttpStatus.BAD_REQUEST, reason = "Some parameters are invalid")

Also note, that Spring only uses _@ResponseStatus_, when **the marked method completes successfully** (without throwing an _Exception_).

We have three ways to use _@ResponseStatus_ to convert an _Exception_ to an HTTP response status:
- using _@ExceptionHandler_
- using _@ControllerAdvice_
- marking the _Exception_ class
---

# **@ControllerAdvice**
## What is @ControllerAdvice Actually?
Think of it as:
> A global interceptor/helper for all controllers.

Global excpetion handles its placed on a class.
Spring says:
> Put all exception handling in one place.

```
@ControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(UserNotFoundException.class)
    public ResponseEntity<String> handleUser(
            UserNotFoundException ex) {
        ...
    }

    @ExceptionHandler(ProductNotFoundException.class)
    public ResponseEntity<String> handleProduct(
            ProductNotFoundException ex) {
        ...
    }

    @ExceptionHandler(Exception.class)
    public ResponseEntity<String> handleGeneric(
            Exception ex) {
        ...
    }
}
```

### What happens if both local and global handlers exist?
✅ Local controller handler.
Order
1. Controller's @ExceptionHandler
2. @ControllerAdvice
3. Spring default handling
### Why use @ControllerAdvice?
Answer:
> `@ControllerAdvice` provides centralized exception handling across all controllers. It removes duplicated error-handling logic, ensures consistent API responses, and improves maintainability.

## @RestControllerAdvice

> `@RestControllerAdvice` is a convenience annotation that combines `@ControllerAdvice` and `@ResponseBody`. It is typically used in REST APIs to return JSON/XML responses directly, whereas `@ControllerAdvice` is commonly used in Spring MVC applications that return views.

If you return a `ResponseEntity`, Spring will still serialize the body to JSON (assuming Jackson is on the classpath, which it is in Spring Boot starters).

**Does `ResponseEntity` require `@ResponseBody`?**
Answer:
> No. `ResponseEntity` itself represents the complete HTTP response, and Spring uses `HttpMessageConverters` to write its body. Therefore, a `ResponseEntity` returned from an `@ExceptionHandler` in a `@ControllerAdvice` will still be serialized correctly.

## @Validated
enables method-level validation on a Spring bean. It validates constraints directly placed on method parameters or return values. For validating fields inside a complex object, I use `@Valid` on that parameter so validation cascades into the object's properties.

**How does validation work internally for `@Valid` and `@Validated`?**
> `@Valid` on controller request objects is handled by Spring MVC during request processing and does not rely on AOP proxies. `@Validated` on Spring beans such as services enables method-level validation through a Spring proxy. The proxy intercepts method calls, performs validation, and then invokes the target method. Because it relies on proxies, self-invocation bypasses validation when using `@Validated`.
