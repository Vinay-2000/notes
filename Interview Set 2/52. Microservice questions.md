### What is the disadvantage of API gateway?
|**Disadvantage**|**Root Cause**|**Impact**|
|---|---|---|
|**Single Point of Failure**|Centralized entry point for all traffic|Full system downtime if the gateway fails|
|**Added Latency**|Network hop + middleware processing|Slower API response times|
|**Operational Overhead**|Complex routing/security rules|Increased management complexity|
|**Team Bottlenecks**|Centralized ownership of gateway configs|Slower deployment cycles for new services|
|**Monolithic Risk**|Leaking domain logic into gateway scripts|Unmaintainable gateway codebase|

| **Objective**                  | **Architectural Solution**                                                           |
| ------------------------------ | ------------------------------------------------------------------------------------ |
| **Prevent SPOF**               | Multi-AZ deployment behind a Layer 4 NLB + Multi-Region Geo-DNS.                     |
| **Prevent Crashes**            | Keep gateway instances 100% stateless; use external Redis cluster for rate limiting. |
| **Reduce Processing Time**     | Use Non-Blocking I/O (Envoy/Netty) + Local in-memory JWT key caching.                |
| **Reduce Network Latency**     | HTTP/2 or HTTP/3 at edge + Connection Pooling to downstream services.                |
| **Prevent Cascading Failures** | Fail-fast with Circuit Breakers and short request timeouts.                          |

### How microservice will communicate with each other ?

Microservices communicate with each other using two primary patterns: **Synchronous (Request-Response)** and **Asynchronous (Event-Driven / Message-Based)**.

Choosing between them depends on whether the caller needs an **immediate response** or if the task can be processed **independently in the background**.

```
                       ┌────────────────────────────────────────────────────────┐
                       │               INTER-SERVICE COMMUNICATION              │
                       └───────────────────────────┬────────────────────────────┘
                                                   │
                   ┌───────────────────────────────┴───────────────────────────────┐
                   ▼                                                               ▼
     SYNCHRONOUS (Request-Response)                                   ASYNCHRONOUS (Event-Driven)
     [Service A] ──HTTP/gRPC──> [Service B]                           [Service A] ──Publish Event──> [Message Broker]
     * Caller waits for immediate response                            * Caller fires-and-forgets          │
     * Tight runtime coupling                                         * Loose coupling & resilient       ▼
                                                                                                 [Service B]
```

## 1. Synchronous Communication (Request-Response)

In synchronous communication, **Service A** calls **Service B** over a network protocol and **blocks/waits** until Service B completes processing and returns a response.

### A. REST APIs (HTTP / JSON)

- **How it Works:** Standard HTTP/1.1 or HTTP/2 GET, POST, PUT, DELETE requests sending JSON payloads.
    
- **When to Use:** Simple CRUD operations, public-facing or internal service queries where immediate data is required (e.g., `OrderService` requesting `UserService` for profile details).
    
- **Pros:** Standardized, easy to debug, human-readable JSON, massive ecosystem support.
    
- **Cons:** High network latency, heavy payload overhead (text/JSON serialization), tight temporal coupling.
    

### B. gRPC (HTTP/2 / Protocol Buffers)

- **How it Works:** High-performance, open-source Remote Procedure Call (RPC) framework developed by Google that uses binary serialization (**Protocol Buffers**) over **HTTP/2**.
    
- **When to Use:** Low-latency, high-throughput internal microservice-to-microservice communication.
    
- **Pros:** Up to 7x-10x faster than REST/JSON, multiplexed connections, small payload size, auto-generated client/server stubs.
    
- **Cons:** Harder to debug (binary payloads), requires contract files (`.proto`).
    

## 2. Asynchronous Communication (Event-Driven / Messaging)

In asynchronous communication, **Service A** publishes a message or event to a **Message Broker** and immediately continues its work without waiting for a response. **Service B** consumes the message from the broker whenever it is ready.

### A. Publish/Subscribe Events (Kafka, RabbitMQ, NATS)

- **How it Works:** `OrderService` publishes an `OrderPlacedEvent` to an event broker (e.g., Apache Kafka). `InventoryService`, `NotificationService`, and `AnalyticsService` all independently listen to this topic and process the event.
    
- **When to Use:** State-change notifications, background processing, decoupling multi-step business workflows.
    
- **Pros:**
    
    - **Temporal Decoupling:** If `NotificationService` goes down, the event stays in Kafka until it comes back online.
        
    - **Scalability:** Easily add new consumer services without modifying the publisher.
        
- **Cons:** Eventual consistency, complex tracing, harder error handling/dead-letter queues.
    

### B. Point-to-Point Queues (RabbitMQ, AWS SQS)

- **How it Works:** One producer sends a task to a queue, and **exactly one consumer** picks up and processes that task (e.g., `ImageProcessingService` picking up a image-resize task).
    

## 3. Advanced Patterns for Resilient Communication

Direct service-to-service calls can lead to cascading failures if one service becomes slow or goes down. Enterprise microservice architectures use specialized infrastructure patterns to mitigate this:

### A. Service Mesh (mTLS & Sidecar Proxy)

- Tools like **Istio** or **Linkerd** deploy a proxy (e.g., Envoy) alongside every microservice instance.
    
- The proxies handle mutual TLS (mTLS) encryption, service discovery, load balancing, and traffic splitting without changing application code.
    

### B. Circuit Breakers & Retries

- Tools like **Resilience4j** wrap inter-service calls. If `PaymentService` fails repeatedly, the circuit breaker **opens**, instantly failing fast or executing a fallback function to prevent thread pool starvation in `OrderService`.
    

### C. Service Discovery

- Microservices are dynamic and scale up/down. Tools like **Netflix Eureka** or **Kubernetes DNS** automatically resolve dynamic IP addresses so services don't hardcode URLs.
    

## Direct Comparison

| **Feature**             | **REST (HTTP/JSON)**      | **gRPC (HTTP/2)**         | **Event-Driven (Kafka/RabbitMQ)**    |
| ----------------------- | ------------------------- | ------------------------- | ------------------------------------ |
| **Communication Style** | Synchronous               | Synchronous               | Asynchronous                         |
| **Data Format**         | Text (JSON / XML)         | Binary (Protobuf)         | Binary or JSON                       |
| **Coupling**            | High (Temporal & Spatial) | High (Temporal & Spatial) | Low (Decoupled)                      |
| **Best For**            | External APIs, Web/Mobile | High-speed internal calls | Event notifications, async workflows |
| **Latency**             | Moderate (10–50ms)        | Very Low (1–5ms)          | Low to Medium (near real-time)       |

### Components of Microservices

A microservices architecture relies on a collection of core infrastructure components working together to route requests, manage state, enforce security, and maintain system availability.

## Key Components of Microservices Architecture

|**Component**|**Primary Function**|**Common Tech Stack**|
|---|---|---|
|**API Gateway**|Single entry point for client requests; handles routing, SSL termination, rate limiting, and authentication.|Spring Cloud Gateway, Kong, NGINX, AWS API Gateway|
|**Service Registry & Discovery**|Dynamic directory keeping track of active service instances and their IP addresses/ports.|Netflix Eureka, HashiCorp Consul, Kubernetes DNS|
|**Core Business Services**|Autonomous, loosely coupled services handling specific business domains (e.g., Payment, Order, User).|Spring Boot, Node.js, Go, ASP.NET Core|
|**Database per Service**|Dedicated data storage per service to ensure loose coupling and independent scalability.|PostgreSQL, MongoDB, Redis, MySQL|
|**Event Broker / Message Bus**|Facilitates asynchronous communication and event-driven decoupling between services.|Apache Kafka, RabbitMQ, AWS SNS/SQS|
|**Config Server**|Externalized, centralized configuration management across environments (Dev, QA, Prod).|Spring Cloud Config, HashiCorp Vault, Kubernetes ConfigMaps|
|**Circuit Breaker**|Prevents cascading failures by tripping when downstream services become unresponsive or slow.|Resilience4j, Istio|
|**Observability (Tracing & Logs)**|Aggregates distributed logs and visualizes request flows across multi-service boundaries.|OpenTelemetry, Jaeger, Zipkin, ELK Stack, Grafana Loki|

## How Components Interact

```
[ Client / Web UI ]
        │
        ▼
┌──────────────────┐       ┌──────────────────────────┐
│   API Gateway    │ ───►  │ Service Registry         │
└────────┬─────────┘       │ (Eureka / Consul)        │
         │                 └──────────────────────────┘
         ├───────────────────────┐
         ▼                       ▼
┌──────────────────┐    ┌──────────────────┐
│ Payment Service  │    │ Order Service    │
│  (Spring Boot)   │    │  (Spring Boot)   │
└────────┬─────────┘    └────────┬─────────┘
         │                       │
         ▼                       ▼
┌──────────────────┐    ┌──────────────────┐
│ Payment DB       │    │ Event Broker     │ (Kafka / RabbitMQ)
│ (PostgreSQL)     │    └────────┬─────────┘
└──────────────────┘             │
                                 ▼
                        ┌──────────────────┐
                        │ Inventory Service│
                        └──────────────────┘
```

1. **Routing:** The client sends an HTTP request to the **API Gateway**.
    
2. **Lookup:** The API Gateway queries the **Service Registry** to discover the healthy instance IPs for the requested service.
    
3. **Execution:** The request is forwarded to the appropriate **Business Service**, which reads/writes to its own **Database**.
    
4. **Decoupled Workflow:** For non-blocking operations, the service emits an event to the **Event Broker**, triggering actions in other downstream microservices.
