
| Challenge                        | What happens                                                      | Typical solution                                                     |
| -------------------------------- | ----------------------------------------------------------------- | -------------------------------------------------------------------- |
| **1. Distributed communication** | Services need to communicate over network instead of method calls | REST/gRPC, timeouts, retries, circuit breakers                       |
| **2. Network failures** ⭐        | Requests can timeout, fail, or become slow                        | Timeout, retry with backoff, circuit breaker                         |
| **3. Data consistency** ⭐        | Each service may have its own database                            | Events, Saga pattern, eventual consistency                           |
| **4. Distributed transactions**  | One business operation may involve multiple services              | Saga / compensating transactions                                     |
| **5. Service discovery**         | Service instances can change dynamically                          | Service discovery, Kubernetes DNS, service registry                  |
| **6. Observability** ⭐           | One request can travel through many services                      | Centralized logs, metrics, distributed tracing                       |
| **7. Deployment complexity**     | Many services need to be built/deployed independently             | CI/CD, containers, Kubernetes/ECS                                    |
| **8. Testing**                   | Testing a single service may require multiple dependent services  | Integration tests, contract testing, test containers                 |
| **9. Configuration management**  | Many services need environment/configuration values               | Centralized configuration, environment variables, secrets management |
| **10. Security**                 | Many service-to-service communication paths                       | JWT/OAuth2, TLS/mTLS, IAM, API Gateway                               |
| **11. Versioning**               | Changing one service API can affect consumers                     | Backward-compatible APIs, API versioning, contract testing           |
| **12. Debugging**                | Failure can occur somewhere across many services                  | Correlation IDs + distributed tracing                                |
| **13. Message/event problems**   | Messages can be duplicated, delayed, or arrive out of order       | Idempotency, retries, DLQ, ordering strategies                       |
| **14. Resource/cost overhead**   | More services mean more infrastructure and operational overhead   | Right-sizing, autoscaling, monitoring                                |
