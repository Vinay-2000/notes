# 1) What is Entity Lifecycle?

An Entity Lifecycle defines the different states an entity object goes through from the moment it is created until it is removed from the database.

Hibernate tracks these states using the **Persistence Context (First Level Cache)**.

There are **4 states**:

1. Transient
    
2. Persistent (Managed)
    
3. Detached
    
4. Removed


---

## Lifecycle Diagram

```text
new Employee()
      |
      | persist()
      v
+----------------+
|  Persistent    |
|   (Managed)    |
+----------------+
      |
      | Session Close / detach() / clear()
      v
+----------------+
|   Detached     |
+----------------+
      |
      | merge()
      v
+----------------+
|  Persistent    |
+----------------+
      |
      | remove()
      v
+----------------+
|    Removed     |
+----------------+
      |
      | Commit
      v
Database Row Deleted
```

---

## 1. Transient State

The object exists only in Java memory.

Hibernate does **not** know about it.

Database also doesn't know about it.

Example:

```java
Employee emp = new Employee();
emp.setName("Vinay");
```

At this point:

- Exists only in JVM
    
- No Primary Key (usually)
    
- Not present in Persistence Context
    
- No SQL generated
    

Diagram:

```text
JVM
---------
Employee Object

Database
---------
Nothing
```

---

## 2. Persistent (Managed) State

The object becomes managed by Hibernate.

Example:

```java
entityManager.persist(emp);
```

or

```java
repository.save(emp);
```

Now Hibernate stores the object inside the Persistence Context.

Diagram:

```text
Persistence Context
-------------------------
Employee(id=1)

Database
-------------------------
Employee(id=1)
```

Characteristics:

- Hibernate tracks every field.
    
- Dirty Checking is enabled.
    
- Changes are automatically synchronized with the database.
    
- No explicit update() is required.


Example:

```java
emp.setSalary(60000);
```

No save() required.

Hibernate detects the change automatically.

---

## 3. Detached State

Suppose:

```java
entityManager.close();
```

or

```java
entityManager.clear();
```

The object still exists in Java memory.

But Hibernate stops managing it.

Diagram:

```text
JVM
------------
Employee

Persistence Context
------------
Empty
```

Now:

```java
emp.setSalary(70000);
```

Hibernate does nothing.

No update SQL will be generated.

---

## 4. Removed State

Suppose:

```java
entityManager.remove(emp);
```

Entity enters Removed state.

It is still inside the Persistence Context.

But Hibernate marks it for deletion.

Actual SQL executes during flush/commit.

```sql
DELETE FROM employee
WHERE id = 1;
```

After commit:

Object no longer exists in the database.

---

## State Transitions

|Current State|Operation|Next State|
|---|---|---|
|Transient|persist()|Persistent|
|Persistent|detach(), clear(), close()|Detached|
|Detached|merge()|Persistent|
|Persistent|remove()|Removed|

---

## Internal Working

```text
new Employee()
      |
Transient
      |
persist()
      |
Persistence Context
      |
Managed Entity
      |
Modify Fields
      |
Dirty Checking
      |
flush()
      |
SQL UPDATE
```

Notice:

Dirty Checking works **only** for Persistent entities.

---

## Why is this important?

Hibernate knows:

- Which objects changed
    
- Which should be inserted
    
- Which should be updated
    
- Which should be deleted
    

Without these states, Hibernate would have to compare every object manually.

---

## Common Interview Questions

## Q: Which state supports Dirty Checking?

Persistent (Managed)

---

## Q: Which state is stored in the Persistence Context?

Persistent (Managed)

---

## Q: Does modifying a Detached entity update the database?

No.

Hibernate is no longer tracking it.

---

## Q: Can a Detached entity become Persistent again?

Yes.

Using:

```java
entityManager.merge(entity);
```

---

## Q: Does persist() immediately execute INSERT?

Not necessarily.

Hibernate usually delays the INSERT until:

- flush()
    
- commit()
    

unless it needs the ID immediately.

---

## Memory Trick

```text
Transient
---------
Hibernate doesn't know me.

Persistent
---------
Hibernate is watching me.

Detached
---------
Hibernate forgot me.

Removed
---------

```

---

# Interview Answer

An entity in JPA/Hibernate goes through four lifecycle states: Transient, Persistent, Detached, and Removed. A Transient entity exists only in memory and is not managed by Hibernate. Calling `persist()` moves it to the Persistent state, where it is managed inside the Persistence Context, enabling features like Dirty Checking and automatic synchronization with the database. When the Persistence Context is cleared or closed, the entity becomes Detached, meaning changes to it are no longer tracked. Calling `merge()` reattaches it and returns a managed instance. Finally, calling `remove()` marks the entity for deletion, and Hibernate executes the DELETE statement during flush or transaction commit.

# 2) persist() vs save()

This is a common Hibernate interview question.

The first thing to know is:

- `persist()` belongs to **JPA**
    
- `save()` belongs to **Hibernate**
    

In Spring Boot, since we usually program against JPA, **`persist()`**** is preferred**.

---

## Comparison

|Feature|persist()|save()|
|---|---|---|
|Defined In|JPA (`EntityManager`)|Hibernate (`Session`)|
|Standard API|✅ Yes|❌ No|
|Return Type|`void`|Returns generated ID (`Serializable`)|
|Entity State|Makes a Transient entity Persistent|Makes a Transient entity Persistent|
|SQL Execution|Usually during flush/commit|May execute immediately for IDENTITY, otherwise usually at flush|
|Recommended|✅ Yes|Only when directly using Hibernate|

---

## persist()

Example:

```java
Employee emp = new Employee();
emp.setName("Vinay");

entityManager.persist(emp);
```

Flow:

```text
Transient
    |
persist()
    |
Persistent
    |
flush()/commit()
    |
INSERT INTO employee...
```

Notice:

```
persist()
```

returns:

```java
void
```

Hibernate simply starts managing the object.

---

## save()

Example:

```
Session session = entityManager.unwrap(Session.class);

Long id = (Long) session.save(emp);
```

Flow:

```text
Transient
    |
save()
    |
Persistent
    |
Returns generated ID
```

Unlike `persist()`, it returns:

```java
101L
```

the generated primary key.

---

## Internal Working

Suppose:

```
Employee emp = new Employee();
```

Initially:

```text
Persistence Context

(empty)
```

Call:

```
entityManager.persist(emp);
```

Now:

```text
Persistence Context

Employee(id=1)
```

Hibernate now tracks this object.

When the transaction commits:

```sql
INSERT INTO employee(...)
VALUES(...);
```

is executed.

---

## What if the entity already exists?

Suppose:

```
Employee emp = new Employee();
emp.setId(1L);

entityManager.persist(emp);
```

Hibernate assumes:

> "This is a brand new entity."

It will attempt an INSERT.

If ID 1 already exists:

```text
EntityExistsException
```

or a database primary key violation occurs.

`persist()` is only for **new entities**.

---

## ID Generation Example

Suppose:

```
@Id
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;
```

### persist()

```
entityManager.persist(emp);
```

Hibernate may execute the INSERT immediately because it needs the generated ID from the database.

---

### save()

```
session.save(emp);
```

Returns:

```java
101L
```

because `save()` always returns the generated identifier.

---

## Why does JPA recommend persist()?

Because JPA is a specification.

Code written using:

```
entityManager.persist()
```

can work with:

- Hibernate
    
- EclipseLink
    
- OpenJPA
    

without modification.

Using:

```
session.save()
```

ties your application to Hibernate.

---

## Common Interview Questions

### Q: Which one should we use in Spring Boot?

Answer:

```text
persist()
```

or simply:

```java
repository.save(entity);
```

because Spring Data JPA internally works with JPA.

---

### Q: Does persist() immediately execute INSERT?

No.

Usually INSERT happens during:

- flush()
    
- commit()
    

However, with some ID generation strategies (like `IDENTITY`), Hibernate may execute the INSERT earlier to obtain the generated ID.

---

### Q: Can persist() update an existing entity?

No.

It is only for new entities.

---

### Q: Do both make the entity Persistent?

Yes.

Both move a Transient entity into the Persistent (Managed) state.

---

## Memory Trick

```text

---------

Returns nothing

---------

```

# Interview Answer

`persist()` and `save()` are both used to make a transient entity persistent. The main difference is that `persist()` is defined by the JPA specification and returns `void`, whereas `save()` is a Hibernate-specific method that returns the generated primary key. Both register the entity with the Persistence Context, and Hibernate normally executes the INSERT during flush or transaction commit, although it may insert earlier for strategies like `IDENTITY` to obtain the generated key. In Spring Boot applications, `persist()` or `repository.save()` is generally preferred because it follows the JPA standard and keeps the code provider-independent.

| Method                    | Existing Entity                                        |
| ------------------------- | ------------------------------------------------------ |
| `entityManager.persist()` | ❌ Tries INSERT → Exception                             |
| `Session.save()`          | ❌ Tries INSERT → Exception                             |
| `JpaRepository.save()`    | ✅ Calls `merge()` and updates (or attaches) the entity |

# 3) merge() vs update()

This question is usually asked after understanding the Entity Lifecycle.

The first thing to know is:

- `merge()` belongs to **JPA (****`EntityManager`****)**
    
- `update()` belongs to **Hibernate (****`Session`****)**
    

Both are primarily used to work with **Detached** entities.

---

## Why do we need them?

Suppose:

```java
Employee emp = repository.findById(1L).get();
```

The entity is now **Persistent**.

Later:

```java
entityManager.close();
```

Now:

```text
Employee
---------
Detached
```

You modify it:

```java
emp.setSalary(60000);
```

Hibernate will **not** update the database because the entity is Detached.

To make Hibernate manage it again, you use:

- `merge()`
    
- `update()`
    

---

## Comparison

|Feature|merge()|update()|
|---|---|---|
|Defined In|JPA (`EntityManager`)|Hibernate (`Session`)|
|Standard API|✅ Yes|❌ No|
|Works With|Detached Entity|Detached Entity|
|Returns|Managed Entity|void|
|Original Object|Remains Detached|Becomes Managed|
|If another managed entity with same ID exists|Copies state into managed entity|Throws exception|
|Recommended|✅ Yes|Rarely used in Spring Boot|

---

## merge()

Example:

```java
Employee detached = new Employee();
detached.setId(1L);
detached.setName("Vinay");
```

Call:

```java
Employee managed = entityManager.merge(detached);
```

Flow:

```text
Detached Employee
        |
merge()
        |
Hibernate finds or creates
Managed Employee
        |
Copies all values
        |
Returns Managed Object
```

Notice:

```java
managed == detached
```

is

```text
false
```

Hibernate creates (or finds) a **different managed instance**.

The original object is still Detached.

Diagram:

```text
Detached Object
        |
merge()
        |
        +--------------------+
        |                    |
Detached Object      Managed Object
```

Always continue working with the object returned by `merge()`.

---

## update()

Example:

```java
Session session = entityManager.unwrap(Session.class);

session.update(detached);
```

Flow:

```text
Detached
    |
update()
    |
Persistent
```

Unlike `merge()`:

No new object is created.

The same object becomes managed.

Diagram:

```text
Detached Object
        |
update()
        |
Managed Object
```

---

## What if another managed entity already exists?

Suppose:

```java
Employee e1 = entityManager.find(Employee.class, 1L);
```

Now Hibernate already has:

```text
Employee(id=1)
```

inside the Persistence Context.

Later:

```java
Employee detached = new Employee();
detached.setId(1L);

session.update(detached);
```

Hibernate now sees:

```text
Two Java objects
Same Primary Key
```

It doesn't know which one should represent row 1.

So it throws:

```text
NonUniqueObjectException
```

---

## merge() in the same situation

Instead:

```java
entityManager.merge(detached);
```

Hibernate says:

"I already have a managed entity."

It copies values from:

```text
Detached
```

into

```text
Managed
```

No exception.

---

## Internal Working

### merge()

```text
Detached
      |
      v
Find Managed Entity
      |
Copy Fields
      |
Dirty Checking
      |
UPDATE SQL
```

### update()

```text
Detached
      |
      v
Attach Same Object
      |
Dirty Checking
      |
UPDATE SQL
```

---

## Which one should we use?

In Spring Boot:

```text
merge()
```

or simply

```java
repository.save(entity);
```

because `JpaRepository.save()` internally calls:

```java
entityManager.merge()
```

for existing entities.

---

## Common Interview Questions

### Q: Which one creates a new managed object?

```text
merge()
```

---

### Q: Which one returns an entity?

```text
merge()
```

---

### Q: Which one throws an exception if the Persistence Context already contains the same ID?

```text
update()
```

throws:

```text
NonUniqueObjectException
```

---

### Q: Which one should be preferred?

```text
merge()
```

because it is part of the JPA specification and safely handles existing managed instances.

---

## Memory Trick

```text
merge()
---------
Copies data
Returns new managed object

update()
---------
Attaches same object
No copy
```

---

# Interview Answer

`merge()` and `update()` are used to reattach detached entities. `merge()` is defined by JPA and copies the state of the detached entity into a managed entity, returning the managed instance. The original object remains detached. If a managed entity with the same primary key already exists in the Persistence Context, `merge()` copies the values into it without throwing an exception. `update()` is a Hibernate-specific method that directly reattaches the same detached object to the session. If another managed entity with the same identifier already exists, Hibernate throws a `NonUniqueObjectException`. In Spring Boot applications, `merge()` or `JpaRepository.save()` is generally preferred because it follows the JPA standard and handles detached entities more safely.
# 4) Dirty Checking in Hibernate

Dirty Checking is a Hibernate mechanism that automatically detects changes made to **Persistent (Managed)** entities and synchronizes those changes with the database during `flush()` or transaction commit.

Without Dirty Checking, you would have to explicitly call an update method every time you modified an entity.

---

## Why Do We Need Dirty Checking?

Suppose:

```java
@Transactional
public void updateSalary() {

    Employee emp = repository.findById(1L).get();

    emp.setSalary(60000);

}
```

Notice:

There is **no**:

```java
repository.save(emp);
```

Yet Hibernate still executes:

```sql
UPDATE employee
SET salary = 60000
WHERE id = 1;
```

How?

Because of Dirty Checking.

---

## Internal Working of Dirty Checking

When Hibernate loads an entity:

```java
Employee emp = repository.findById(1L).get();
```

Hibernate stores two things inside the Persistence Context:

```text
Persistence Context

Managed Entity
--------------
Employee
salary = 50000

Snapshot
--------------
salary = 50000
```

The snapshot represents the original state of the entity when it was loaded.

---

Now you modify it:

```java
emp.setSalary(60000);
```

Current state:

```text
Employee
salary = 60000
```

Snapshot:

```text
Employee
salary = 50000
```

---

During `flush()` or transaction commit, Hibernate compares them:

```text
Snapshot
---------
50000

Current Entity
---------
60000
```

Different?

Yes.

Generate:

```sql
UPDATE employee
SET salary = 60000
WHERE id = 1;
```

---

## Dirty Checking Flow

```text
Load Entity
      |
Store Snapshot
      |
Modify Entity
      |
flush()/commit()
      |
Compare Snapshot vs Current
      |
Different?
      |
Yes
      |
Generate UPDATE SQL
```

---

## When Does Dirty Checking Work?

Dirty Checking works only for **Persistent (Managed)** entities.

Example:

```java
Employee emp = repository.findById(1L).get();
```

State:

```text
Persistent
```

Dirty Checking works.

---

Now consider:

```java
entityManager.detach(emp);

emp.setSalary(60000);
```

State:

```text
Detached
```

Hibernate is no longer tracking the entity.

No UPDATE is generated.

---

## What Triggers Dirty Checking?

Dirty Checking happens during:

- `flush()`
    
- Transaction commit
    
- Before executing certain JPQL/Criteria queries (Hibernate automatically flushes in `AUTO` mode to maintain consistency)
    

---

## Does Hibernate Compare Every Object?

No.

Only entities stored in the **Persistence Context** are checked.

Objects created using:

```java
new Employee();
```

are not managed.

Hibernate ignores them.

---

## Performance of Dirty Checking

Dirty Checking is efficient because:

- Hibernate already knows which entities are managed
    
- It compares only managed entities against their snapshots
    
- It does **not** scan every object in JVM memory
    

---

## Common Interview Questions on Dirty Checking

### Does Dirty Checking work for Detached entities?

No.

Hibernate only tracks Persistent entities.

---

### Do I need to call save() after modifying a managed entity?

No.

Dirty Checking automatically detects changes.

---

### When is UPDATE SQL executed?

Usually during:

- `flush()`
    
- Transaction commit
    

Not immediately after calling the setter.

---

### How does Hibernate know what changed?

It keeps a snapshot of the entity's original state inside the Persistence Context and compares it with the current state during flush.

---

## Memory Trick for Dirty Checking

```text
Load Entity
      |
Snapshot Created
      |
Modify Fields
      |
Compare Snapshot
      |
UPDATE if Different
```

---

# Interview Answer

Dirty Checking is a Hibernate feature that automatically detects modifications made to managed entities. When an entity is loaded into the Persistence Context, Hibernate stores a snapshot of its original state. During `flush()` or transaction commit, Hibernate compares the current entity with the snapshot. If any field has changed, Hibernate automatically generates the appropriate `UPDATE` statement. Dirty Checking only works for entities in the Persistent (Managed) state and eliminates the need to explicitly call update methods after modifying managed entities.

# 5) flush() vs commit()

`flush()` and `commit()` are closely related but serve different purposes.

- **flush()** synchronizes the Persistence Context with the database.
    
- **commit()** permanently commits the transaction.
    

A common interview mistake is saying that `flush()` commits the transaction. It does **not**.

---

## Why Do We Need flush()?

Suppose:

```java
@Transactional
public void updateEmployee() {

    Employee emp = repository.findById(1L).get();

    emp.setSalary(60000);

}
```

When you call:

```java
emp.setSalary(60000);
```

Hibernate does **not** immediately execute:

```sql
UPDATE employee
SET salary = 60000
WHERE id = 1;
```

Instead, the change remains only inside the Persistence Context.

Eventually Hibernate must synchronize these changes with the database.

That's what **flush()** does.

---

## Internal Working of flush()

Suppose the Persistence Context contains:

```text
Persistence Context

Employee(id=1)
salary = 60000
```

Database still contains:

```text
Employee
------------
salary = 50000
```

Calling:

```java
entityManager.flush();
```

causes Hibernate to perform Dirty Checking.

```text
Snapshot
------------
50000

Current
------------
60000
```

Difference found.

Hibernate executes:

```sql
UPDATE employee
SET salary = 60000
WHERE id = 1;
```

Now the database row is updated.

**But the transaction is still open.**

Nothing has been committed yet.

---

## What Does commit() Do?

When:

```java
transaction.commit();
```

or when a `@Transactional` method completes successfully:

Spring commits the database transaction.

At commit time Hibernate first performs an automatic flush (if needed), then commits the transaction.

After commit:

- Changes become permanent.
    
- Database locks are released.
    
- Other transactions can safely see the committed changes (depending on isolation level).
    

---

## flush() vs commit()

|Feature|flush()|commit()|
|---|---|---|
|Synchronizes Persistence Context with Database|✅ Yes|✅ Yes (performs a flush first if needed)|
|Ends Transaction|❌ No|✅ Yes|
|Makes Changes Permanent|❌ No|✅ Yes|
|Can Roll Back Changes Afterwards|✅ Yes|❌ No|
|Releases Database Locks|❌ No|✅ Yes|

---

## Example

```java
@Transactional
public void demo() {

    Employee emp = repository.findById(1L).get();

    emp.setSalary(60000);

    entityManager.flush();

    throw new RuntimeException();
}
```

Flow:

```text
Load Entity
      |
Modify Entity
      |
flush()
      |
UPDATE SQL Executed
      |
Exception
      |
Rollback
```

Result:

```text
Database salary = 50000
```

Even though the UPDATE was executed, the transaction was rolled back because it was never committed.

This proves:

> **flush() sends SQL to the database, but commit() makes it permanent.**

---

## Why Does Hibernate Flush Automatically?

By default (`FlushMode.AUTO`), Hibernate flushes:

- Before transaction commit
    
- Before certain JPQL/Criteria queries
    
- When explicitly calling `flush()`
    

This ensures that queries within the same transaction see consistent data.

---

## When Would We Call flush() Manually?

Common use cases:

- Detect database constraint violations early.
    
- Ensure generated IDs are available.
    
- Execute SQL before continuing with more business logic.
    
- Process very large batches by periodically flushing and clearing the Persistence Context.
    

---

## Common Interview Questions on flush() vs commit()

### Does flush() commit the transaction?

No.

It only synchronizes changes with the database.

The transaction remains active.

---

### Can data be rolled back after flush()?

Yes.

If the transaction rolls back, all flushed changes are rolled back as well.

---

### Does commit() automatically call flush()?

Yes.

Before committing, Hibernate flushes any pending changes.

---

### When is SQL usually executed?

Normally during:

- `flush()`
    
- Automatic flush before commit
    
- Automatic flush before certain queries
    

---

## Memory Trick

```text
flush()
--------
Send SQL

commit()
--------
Make it permanent
```

---

# Interview Answer

`flush()` synchronizes the Persistence Context with the database by executing pending SQL statements such as INSERT, UPDATE, and DELETE, but it does not commit the transaction. The transaction remains active, and all flushed changes can still be rolled back. `commit()` finalizes the transaction by first performing a flush if necessary and then permanently committing the changes to the database. In short, `flush()` sends SQL to the database, while `commit()` makes those changes permanent and ends the transaction.

This ensures that queries within the same transaction see consistent data.

---

## When Would We Call flush() Manually?

Common use cases:

- Detect database constraint violations early.
    
- Ensure generated IDs are available.
    
- Execute SQL before continuing with more business logic.
    
- Process very large batches by periodically flushing and clearing the Persistence Context.
    

---

## Common Interview Questions on flush() vs commit()

### Does flush() commit the transaction?

No.

It only synchronizes changes with the database.

The transaction remains active.

---

### Can data be rolled back after flush()?

Yes.

If the transaction rolls back, all flushed changes are rolled back as well.

---

### Does commit() automatically call flush()?

Yes.

Before committing, Hibernate flushes any pending changes.

---

### When is SQL usually executed?

Normally during:

- `flush()`
    
- Automatic flush before commit
    
- Automatic flush before certain queries
    

---

## Memory Trick

```text
flush()
--------
Send SQL

commit()
--------
Make it permanent
```

---

# Interview Answer

`flush()` synchronizes the Persistence Context with the database by executing pending SQL statements such as INSERT, UPDATE, and DELETE, but it does not commit the transaction. The transaction remains active, and all flushed changes can still be rolled back. `commit()` finalizes the transaction by first performing a flush if necessary and then permanently committing the changes to the database. In short, `flush()` sends SQL to the database, while `commit()` makes those changes permanent and ends the transaction.

# 7) Second Level Cache

The Second Level Cache is an optional Hibernate cache that stores entities **across multiple Sessions (EntityManagers)**.

Unlike the First Level Cache, which belongs to a single Persistence Context, the Second Level Cache is shared across multiple Persistence Contexts.

By default, it is **disabled**.

---

## Why Do We Need Second Level Cache?

Suppose two different users request the same employee.

Transaction 1:

```java
Employee emp = repository.findById(1L).get();
```

Hibernate executes:

```sql
SELECT * FROM employee WHERE id = 1;
```

Transaction ends.

---

Transaction 2:

```java
Employee emp = repository.findById(1L).get();
```

Without Second Level Cache:

Hibernate again executes:

```sql
SELECT * FROM employee WHERE id = 1;
```

The database is queried twice.

---

With Second Level Cache:

Transaction 1

```text
Database
     |
SELECT
     |
Store Entity in L2 Cache
```

Transaction 2

```text
Second Level Cache
        |
Entity Found
        |
Return Entity
```

No database query is executed.

---

## Internal Working of Second Level Cache

Request:

```java
repository.findById(1L);
```

Hibernate checks:

```text
First Level Cache
```

Found?

```text
Yes
```

Return entity.

---

If not found:

```text
Second Level Cache
```

Found?

```text
Yes
```

Return entity.

---

If still not found:

```text
Database
```

Execute SQL.

Store entity in:

- First Level Cache
    
- Second Level Cache
    

---

## Second Level Cache Flow

```text
findById(1)
      |
First Level Cache
      |
Found?
  |        |
 Yes      No
  |        |
Return   Second Level Cache
            |
         Found?
        |       |
       Yes      No
        |        |
    Return    Database
    Entity       |
                 |
          Store in L1 + L2 Cache
```

---

## What Is Stored?

Typically:

- Entities
    
- Collections
    
- Natural IDs
    

It does **not** cache arbitrary queries by default.

Query caching is a separate feature.

---

## Cache Providers

Hibernate doesn't implement the cache itself.

It delegates to cache providers such as:

- Ehcache
    
- Caffeine
    
- Hazelcast
    
- Infinispan
    
- JCache (JSR-107)
    

---

## Enabling Second Level Cache

Example:

```properties
spring.jpa.properties.hibernate.cache.use_second_level_cache=true
```

Annotate entity:

```java
@Entity
@Cacheable
@org.hibernate.annotations.Cache(
    usage = CacheConcurrencyStrategy.READ_WRITE
)
public class Employee {
}
```

Only annotated entities are cached.

---

## Cache Concurrency Strategies

|Strategy|Use Case|
|---|---|
|READ_ONLY|Data never changes (Countries, States)|
|READ_WRITE|Frequently read and occasionally updated data|
|NONSTRICT_READ_WRITE|Accepts slightly stale data|
|TRANSACTIONAL|JTA environments requiring transactional cache consistency|

For interviews:

Remember:

```text
READ_ONLY

READ_WRITE
```

These are the most commonly discussed.

---

## First Level Cache vs Second Level Cache

|Feature|First Level Cache|Second Level Cache|
|---|---|---|
|Scope|One Session / EntityManager|Shared across Sessions|
|Enabled by Default|✅ Yes|❌ No|
|Can Be Disabled|❌ No|✅ Yes|
|Location|Persistence Context|External Cache Provider|
|Shared Between Users|❌ No|✅ Yes|
|Lifetime|Session|Until Evicted or Expired|

---

## Common Interview Questions on Second Level Cache

### Is Second Level Cache enabled by default?

No.

It must be explicitly configured.

---

### Does Second Level Cache replace First Level Cache?

No.

Hibernate always checks:

1. First Level Cache
    
2. Second Level Cache
    
3. Database
    

---

### Where is Second Level Cache stored?

In an external cache provider like Ehcache or Caffeine.

It is **not** stored inside the Persistence Context.

---

### Should every entity be cached?

No.

Only frequently read and rarely modified entities are good candidates.

Examples:

- Country
    
- State
    
- Currency
    
- Product Categories
    

Frequently changing entities like orders or bank transactions are generally poor candidates.

---

```text
First Level Cache
-----------------
One Session

Second Level Cache
------------------
All Sessions
```

# Interview Answer

The Second Level Cache is an optional Hibernate cache that stores entities across multiple sessions or EntityManagers. Unlike the First Level Cache, which is local to a single Persistence Context, the Second Level Cache is shared and helps reduce repeated database queries across transactions. Hibernate first checks the First Level Cache, then the Second Level Cache, and finally the database. It is disabled by default and requires a cache provider such as Ehcache or Caffeine. Second Level Cache is best suited for frequently read, rarely updated data.
