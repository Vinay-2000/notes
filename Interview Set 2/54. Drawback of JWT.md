### **1. Difficult to revoke immediately **
Once issued:

```
JWT → valid for 15 minutes
```

Even if the user logs out, the token may remain valid until it expires.
With server-side sessions, you can simply invalidate the session.
**Typical solution:** short-lived access tokens + refresh token revocation.

### **2. Token size**
JWT contains claims:

```
header + payload + signature
```

So it's larger than something like:

```
sessionId = abc123
```

If you send a large JWT on every request:

```
Authorization: Bearer <large-token>
```

there is additional network overhead.

### **3. Information can be read**
JWT payload is normally **encoded, not encrypted**.
So don't put:

```
password
credit-card details
secrets
```

inside it.

### **4. Changing user permissions can be tricky**
Suppose JWT contains:

```
ROLE_ADMIN
```

and you remove the user's admin role in the database.
An existing JWT may still contain:

```
ROLE_ADMIN
```

until it expires.
This is one reason some systems keep access tokens short-lived or re-check user information when necessary.

### **5. Key management becomes important**
If you're using asymmetric signing:

```
Auth Service
Private Key → signs JWT
Microservices
Public Key → verify JWT
```

You now need proper:

- key rotation
- key distribution
- secret/key storage
- expiry of old keys
    **6. JWT doesn't automatically make your system secure**
    You still need to handle:

```
Token expiry
Token storage
HTTPS
Refresh token security
Revocation
Signing keys
CSRF/XSS considerations
```

JWT is just a **token format/mechanism**, not a complete security solution.
