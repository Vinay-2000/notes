Garbage Collection in Java is an automated process managed by the Java Virtual Machine (JVM) that reclaims memory occupied by unreferenced objects on the Heap.

It works in two main phases:

1. **Mark Phase:** Traverses the active application threads and tracks object references starting from **GC Roots** (like stack frames, static variables, active thread contexts) to mark all reachable objects.
    
2. **Sweep Phase (Sweep/Compact):** Reclaims memory used by unreferenced (unreachable) objects and, depending on the algorithm, compacts memory to eliminate heap fragmentation."




Java GC operates on the **Weak Generational Hypothesis**, which states that most objects die short after creation (e.g., local request variables in Spring Boot).

- **Young Generation:**
    
    - **Eden Space:** All new objects are initially allocated here.
        
    - **Survivor Spaces (S0 / S1):** Active objects that survive Minor GC are moved between S0 and S1. One survivor space is always empty during execution.
- Minor garbage collection occurs in Young Generation.
	When minor garbage collection?
	When the young generation fills up, this causes a minor garbage collection.
	All the unreferenced (dead) objects are cleaned up from young generation.
        
- **Old (Tenured) Generation:**
    
    - Holds long-lived objects (e.g., Spring Singletons, long-lived caches).
        
    - Objects are promoted here if they survive a specific threshold of GC cycles (tenuring threshold, default usually 15).
        
- **Metaspace (Off-Heap):**
    
    - Replaced PermGen in Java 8. Stores class metadata, static fields, and method definitions in native OS memory, not on the JVM heap.

- **System.gc() Usage:** Explicitly note that calling `System.gc()` is bad practice in production because it triggers a full, blocking GC run without guarantee of execution. It can be disabled via `-XX:+DisableExplicitGC`.
    
- **Out-of-Memory Errors (OOM):** Mention that `java.lang.OutOfMemoryError: Java heap space` happens when GC cannot reclaim enough memory to allocate a new object even after running a Full GC, usually caused by memory leaks (e.g., static collections retaining references, unclosed stream resources).

##### Suppose we have 4 dependent classes, will the garbage collector work in that case.
 Yes. Garbage collection works regardless of how many objects or dependencies exist. The JVM determines reachability from GC Roots. If a group of dependent objects is no longer reachable from any GC Root, the entire object graph can become eligible for garbage collection, even if the objects reference each other.
