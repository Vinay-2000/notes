# What is Idempotency?

An operation is **idempotent** if performing it multiple times produces the same result as performing it once.

An API is idempotent if making the same request multiple times results in the same final state as making it once. According to HTTP semantics, GET, PUT, DELETE, HEAD, and OPTIONS are idempotent methods. POST is generally not idempotent because repeated requests can create multiple resources. PATCH may or may not be idempotent depending on the operation being performed. A common misconception is that idempotent APIs must return the same response every time; in reality, idempotency is about the final state of the resource, not the response. In distributed systems, idempotency is important for handling retries safely, especially in payment and order-processing APIs.

| Method      | Purpose                                                        | Idempotent? | Safe? |
| ----------- | -------------------------------------------------------------- | ----------- | ----- |
| **GET**     | Retrieve a resource                                            | ✅ Yes       | ✅ Yes |
| **POST**    | Create a new resource or trigger an action                     | ❌ No        | ❌ No  |
| **PUT**     | Create or completely replace a resource                        | ✅ Yes       | ❌ No  |
| **PATCH**   | Partially update a resource                                    | Depends\*   | ❌ No  |
| **DELETE**  | Delete a resource                                              | ✅ Yes       | ❌ No  |
| **HEAD**    | Retrieve only the response headers (no body)                   | ✅ Yes       | ✅ Yes |
| **OPTIONS** | Discover supported HTTP methods and capabilities of a resource | ✅ Yes       | ✅ Yes |

## Q: Does idempotent mean same response?

No.
Very common confusion.
Example:

```
DELETE /user/1
```

Response 1:

```
200 OK
```

Response 2:

```
404 Not Found
```

Different responses.

Still idempotent because resource state is unchanged.
