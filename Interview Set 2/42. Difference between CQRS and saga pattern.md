**CQRS** separates the write (command) and read (query) models so they can be optimized and scaled independently. It's mainly used to improve performance, scalability, and maintainability of applications.
**Saga** is a pattern for managing distributed transactions across multiple microservices. Instead of a single ACID transaction, it coordinates a series of local transactions and, if a step fails, executes compensating actions to maintain eventual consistency.
They solve different problems and are commonly used together in event-driven microservice architectures.

# CQRS (Command Query Responsibility Segregation)

CQRS says:

> Don't use the same model for both reading and writing.
> Instead split them into:

- **Command Side** → Creates, updates, deletes data
- **Query Side** → Reads data
    The read database can be
- Redis
- Elasticsearch
- Replica DB
- Materialized View
    because reading requirements are different.

### Why?

Writing

```
Insert order
Validate inventory
Calculate taxes
Generate invoice
```

Reading

```
Show last 10 orders
Search by status
Sort by date
```

## Very different workloads.

### Benefits

- Faster reads
- Scale reads independently
- Optimized models
- Better performance

---

### Downside

Read model is usually eventually consistent.

# CQRS Example

Imagine YouTube.

Uploading a video

```
Upload Video
Generate Thumbnail
Store Metadata
```

That's the write model.

Viewing videos

```
Search
Trending
Recommendations
Watch History
```

Uses a highly optimized read model.

That's CQRS.

# Can they be used together?

Yes.

Example

```
Order Placed
      ↓
Saga starts
      ↓
Reserve Inventory
      ↓
Payment
      ↓
Shipping
      ↓
Order Completed
      ↓
Event Published
      ↓
CQRS Read Model Updated
```

The Saga coordinates the workflow, while CQRS updates the read side.

| CQRS                                | Saga                                             |
| ----------------------------------- | ------------------------------------------------ |
| Separates read and write operations | Manages distributed transactions across services |
| Solves scalability and complexity   | Solves data consistency without 2PC              |
| Focuses on how data is accessed     | Focuses on coordinating business workflows       |
| Usually within one service          | Usually across multiple services                 |
