
Optimistic locking is a concurrency control mechanism used by JPA and Hibernate to prevent lost updates without locking database rows. It works by maintaining a version field, typically annotated with `@Version`. 
When an entity is updated, Hibernate includes the current version in the SQL `WHERE` clause. If another transaction has already modified the row, the version changes, the update affects zero rows, and Hibernate throws an `OptimisticLockException`. This approach assumes conflicts are rare, so it provides better concurrency and performance than pessimistic locking by avoiding database locks.
# Why is it called "Optimistic"?

Because it is **optimistic**.

It assumes: Conflicts are rare.
So:
- Don't lock rows.
- Let everyone work.
- Check for conflicts only at commit/update time.

```
@Entity
public class Employee {

    @Id
    private Long id;

    private double salary;

    @Version //Hibernate/JPA expects (or creates, if using DDL generation) a real column
    private Integer version;
}
```

### User A updates

Hibernate executes:
```
UPDATE employee
SET salary = 60000,
    version = 2
WHERE id = 1
AND version = 1;
```
One row updated.
Success.

Database:

| Salary | Version |
| ------ | ------- |
| 60000  | 2       |

---

### User B updates

Hibernate executes:

```
UPDATE employee
SET salary = 55000,
    version = 2
WHERE id = 1
AND version = 1;
```

But database version is already:

```
2
```

So:

```
0 rows updated
```

Hibernate throws:

```
OptimisticLockException
```

Update rejected.
# Optimistic vs Pessimistic Locking

| Optimistic                      | Pessimistic                           |
| ------------------------------- | ------------------------------------- |
| No database lock                | Database row lock                     |
| Detects conflicts during update | Prevents conflicts immediately        |
| Better performance              | Lower concurrency                     |
| Best when conflicts are rare    | Best when conflicts are common        |
| Uses `@Version`                 | Uses `LockModeType.PESSIMISTIC_WRITE` |
# Common Interview Questions

### Q: Does Optimistic Locking lock the row?

No.

It never locks the row.

It only checks the version during update.

---

### Q: Who updates the version?

Hibernate automatically.

---

### Q: What exception is thrown?

```
OptimisticLockException
```

(or Spring translates it into an appropriate `DataAccessException` hierarchy depending on the context.)

---

### Q: Can Optimistic Locking prevent dirty reads?

No.

Optimistic locking is **not an isolation level**.

It only prevents **lost updates**.

---

# Optimistic Locking vs Isolation

Many candidates confuse these.

| Isolation Level                             | Optimistic Locking           |
| ------------------------------------------- | ---------------------------- |
| Database transaction feature                | JPA/Hibernate feature        |
| Prevents dirty/non-repeatable/phantom reads | Prevents lost updates        |
| Controls concurrent reads/writes            | Detects conflicting updates  |
| Works during transaction execution          | Checks at update/commit time |
**Q: When is the lock acquired in pessimistic locking?**
```
@Lock(LockModeType.PESSIMISTIC_WRITE)
Employee findById(Long id);
```
Answer:

> The lock is acquired when the row is read with a pessimistic lock, typically using `SELECT ... FOR UPDATE` or JPA's `LockModeType.PESSIMISTIC_WRITE`. The database holds the lock until the transaction commits or rolls back, preventing other transactions from updating the same row.
